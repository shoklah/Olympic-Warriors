# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Olympic Warriors is a tool for running a multi-discipline sports event (rugby, dodgeball, blindtest, relay, etc.) across yearly "editions". Two deployable parts:

- `server/` — Django 4.2 + Django REST Framework API (single app `olympic_warriors`), PostgreSQL only (no sqlite fallback).
- `front/` — SvelteKit 2 / Svelte 4 (plain JS, no TypeScript; Vitest unit and component tests, no lint tooling) served via `adapter-node`.

`client/` is an empty leftover directory. `nginx/nginx.conf` is a dev-only config that no compose file references; production nginx config lives on the host under `nginx/user_conf.d` (not in the repo).

## Commands

Everything runs through the root `docker-compose.yml` (server on 3003, Postgres on **5433**, pgadmin on 5051, front on 5173). `server/docker-compose.yml` is a stale near-duplicate on port 5432; ignore it.

```bash
docker compose up --build              # migrate + runserver + vite dev
docker compose up -d -V --build front  # after a front dependency or Dockerfile change: node_modules is an anonymous volume, -V renews it
docker compose exec server python manage.py test                       # all Django tests (needs Postgres)
docker compose exec server python manage.py test olympic_warriors.tests.test_players.TestPlayersAPI.test_get_players
docker compose exec server python manage.py makemigrations
docker compose exec server python manage.py createsu                   # superuser from SU_USERNAME/SU_PASSWORD
docker compose exec server python manage.py create_tokens_for_users    # backfill DRF tokens
docker compose exec server python manage.py export_edition 2026 --out /server/edition-2026.json   # edition -> JSON without ids
docker compose exec server python manage.py import_edition /server/edition-2026.json --dry-run     # add --replace to overwrite that year
docker compose exec server python manage.py refresh_badges             # rebuild the computed badges (a host crontab runs it nightly in prod)
pylint --load-plugins pylint_django --ignore=lib server/               # what CI runs (advisory, no .pylintrc)
```

Front (inside `front/`): `npm run dev`, `npm run build`, `npm run preview`. There is no `check` or `lint` script. `npm test` runs Vitest once over `src/**/*.test.js` (`vite.config.js`: jsdom, `src/setupTests.js` loading `@testing-library/jest-dom/vitest`, components rendered with `@testing-library/svelte`); summary fixtures live in `front/src/lib/fixtures/summary.js`.

Required env files, both gitignored:
- `server/dev.env` (copy `server/.env.example`); `ENV=prod` selects `server/prod.env`. Any real env var overrides the file. `ALLOWED_HOSTS` must include `server`, the hostname the front container uses, or every front page 400s. The file is read at startup: `docker compose restart server` after editing it.
- `front/.env` (copy `front/.env.example`) with `API_URL=http://server:3003` (in compose) or `http://localhost:3003`. `API_URL` is `$env/static/private`, so it is baked in at build time; a missing file fails the production build, and in dev `src/lib/server/urls.js` throws a clear error instead of fetching `undefined/...`. In production the `front` container must also get `ORIGIN=https://<public host>` (an adapter-node runtime variable, set in the compose file): SvelteKit's CSRF check compares the browser's `Origin` with it, and the `/lang` language switch is a form POST, so without it every switch is refused with a 403 behind the TLS-terminating nginx. It also needs `ADDRESS_HEADER=x-forwarded-for` for `getClientAddress()` to see the visitor rather than nginx, which the login action forwards to the API's throttle; set it only if the nginx location proxying to the front sets `X-Forwarded-For` (`$proxy_add_x_forwarded_for`), otherwise the header is the visitor's own and forgeable. Without it every login through the site shares nginx's bucket.

CI (`.github/workflows/test.yml`) has two jobs. `test` runs pylint with `continue-on-error` and boots the compose stack; its migrate/test steps are commented out, so the Django side is not a gate. `front` (Node 22) runs `npm ci`, writes a throwaway `.env`, then `npm test` and `npm run build` — that one does gate, so a failing front test or build fails the workflow.

## Backend architecture

**Business logic lives in model `save()` overrides, not views, signals, or services.** Bulk operations (`bulk_create`, `queryset.update()`, `loaddata`) bypass all of it.

Domain: `Edition` owns `Team`s, `Player`s (wraps `auth.User` plus rating facets) and `Discipline`s. `Edition.year` is **unique** — it is the key the front routes and the export/import commands address an edition by, not the pk — and `Edition.photos_url` is an optional link to an external album (migration `0027`) that the front turns into a Photos tab. `Discipline.teams` is M2M through `TeamResult` (points or time, per `ResultTypes`). Team sports have `TeamSportRound`s of `Game`s; `GameEvent` subclasses (`RugbyEvent`, `DodgeballEvent`) log per-player actions and roll scores up into `Game.score*`, and `Game.save()` **recomputes** `TeamResult.points` for every team the game touches from the discipline's active, **played** games of active rounds (3 per win, 1 per draw), so score edits, flag flips, team swaps and soft deletes all resync and an unplayed game counts for nothing. `Game.is_played` is a manual boolean (default `False`, migration `0028` backfilled every existing game to `True`); the schedulers create games unplayed and `GameAdmin.list_editable` lets organisers flip it in the changelist. Points of disciplines without games are entered by hand and never recomputed. Rankings are never stored: `olympic_warriors/standings.py` computes an edition's whole standings in one pass (`compute_standings(edition)`: three queries, then discipline ranks gated by `Discipline.reveal_score`, points disciplines breaking ties on the points difference summed from active, played `Game` scores of active rounds, global points with the podium bonus among the discipline's active results of active teams, team totals and ranks). `Standings.disciplines_of(team_id)` returns a team's `DisciplineStanding`s (discipline id, name, standing, result type, stored points) in discipline id order from the same loaded rows, so it costs no query. `TeamResult.ranking`/`points_difference`/`global_points` and `Team.total_points`/`ranking` delegate to it, recomputing the edition on each access, so read many rows through `compute_standings` once, never through the properties in a loop (the older `TeamSerializer` list views still do, a known fan-out). Team totals sum the active disciplines only: a soft-deleted discipline drops out of them. `Team.final_rank` (migration `0031`, `list_editable` in `TeamAdmin`) records a finishing order by hand for an edition without result data: once any active team of an edition has one (`Edition.ranking_is_manual`), the team ranking is that order (`None` for a team without) and every `total_points` is `None`. `Discipline.get_ranking()` is a dead stub.

**Adding a discipline** (Django multi-table inheritance, `Discipline` is concrete):
1. `models/<Name>.py`: subclass `Discipline`, override `save()` to set `self.name` and `self.result_type` when `self.pk is None`, then call `super().save()`. See `models/Relay.py` for the minimal version, `models/Rugby.py` for one with a `GameEvent` subclass and scoring.
2. Export it from `models/__init__.py`.
3. `site.register(<Name>, DisciplineAdmin)` in `admin.py`.
4. `makemigrations` (each discipline gets its own table).
5. Add a matching SVG in `front/src/lib/img/icons/` — `iconFor()` in `front/src/lib/icons.js` derives the file stem from the discipline name, so a missing icon falls back to `default.svg`. Add the name to `DISCIPLINE_NAMES` in `front/src/lib/icons.test.js`, which fails until the icon exists **and** the name is in `FRENCH_NAMES` or `SAME_IN_FRENCH` in `front/src/lib/i18n/disciplines.js`.
6. Pick its god in `FAMILIES` in `server/olympic_warriors/badges.py`. Its kind in `KINDS` follows: mind under Athena, physical under any other god; add the name to `MINDS` for a mind discipline of another god (as Blindtest under Apollo), or exclude it from `KINDS` next to Fair when it is neither. `test_badges.py` fails when a `Discipline` subclass is missing from `FAMILIES` or, Fair aside, from `KINDS`.

The base `Discipline.save()` creates a `TeamResult` per active team on first save (`points` starts at `0` only for a points discipline with a pairing system, whose games compute it; a discipline without games and every `time` start at `None`, so "no result yet" is a null, never a zero, and switching a discipline to a pairing system later zeroes any null points before scheduling; `BlindtestGuess.save()` adds 1 per `is_artist_correct`/`is_song_correct` flipped on and takes it back when flipped off, onto that null-as-zero, in the result of its round's blindtest; a team created after the blindtest gets its result created on its first point, a guess for a team of another edition is refused on every save with a `ValidationError`, in the admin form through `clean()`) and dispatches scheduling by `pairing_system`, both on creation and when the pairing system is later set on a discipline with no round yet: round robin (`schedule/round_robin.py`, a full circle-method round robin up front with referee assignment, `max_rounds` defaulting to a single round robin) or Swiss (`schedule/swiss.py`, next round only, re-triggered when a `TeamSportRound.is_over` flips, `max_rounds` defaulting to log2 of the team count). The schedulers use `apps.get_model()` to avoid circular imports.

Discipline-specific admin and validation match on the discipline **name string** (`GameAdmin.get_inline_instances`, `RugbyEvent._discipline_validation`); renaming a discipline breaks scoring.

**Registration import:** saving an `Edition` with a new `registration_form` CSV runs `Edition.create_players_from_registration_form`, which delegates to `olympic_warriors/registration.py`. Columns are matched by stable fragments (the bracketed skill criterion such as `[Cardio]`, the prefix of the global-level question, `Prénom et Nom`, optional `Adresse e-mail`), so yearly wording changes need no code change. The skill set itself is versioned in `FORM_PROFILES` (`"2024"`: ten skills with `Observation et orientation` and a single `Endurance et cardio`; `"2025"`: the 2025/2026 set, also exported as `RATINGS`); `resolve_columns` returns the first profile whose criteria all match and `compute_ratings` weights with that profile's coefficients, so a form with a new skill set needs a new profile (each `id` at most 4 characters, the `PlayerRating.identifier` limit). The Edition row and the import share one transaction, returning players are linked by name-derived username (accents kept), the form email is stored when present, and both `Player` and `PlayerRating` rows are update-or-created so re-uploading a corrected form refreshes ratings without duplicates. `Player.rating` is the rounded global rating.

**Edition transfer:** `olympic_warriors/transfer.py` moves a whole edition between databases (local to prod). The export carries no database ids (users by username, rows cross-referenced by throwaway `_id`s, MTI children as `subclass`/`child`); the import inserts with `save_base(raw=True)` so no model `save()` side effect runs, reuses existing users by username and creates missing ones with a random password. Media files are not in the document; on prod, `mediafiles` is a docker volume, so copy them into the container (`docker compose cp`), not into the repo folder. Badges are not exported (`transfer.NOT_EXPORTED`: `Badge`, `BadgeRefresh`; `test_transfer.py` fails when a root model is neither exported nor listed there): a real `import_edition` rebuilds the computed ones with `badges.refresh()` once the import has committed, manual badges are not transferred, and `--replace` cascade-deletes the replaced edition's badges. The runbook is in the transfer design spec under `docs/superpowers/specs/`.

**API:** ~70 flat `@api_view` functions in `views.py` wired in one hand-written list in `urls.py` (no routers, no `/api/` prefix except the schema at `/api/schema/swagger/`). Global auth is DRF `TokenAuthentication` + `IsAuthenticated`. Six edition/discipline read views and the two profile views (`GET /profiles/`, the leaderboard; `GET /profile/<user_id>/`, 404 for someone who never played) carry `@permission_classes([AllowAny])` below `@api_view` and are public; everything else returns 401 without a token. `/profiles/` rows carry `places` (`[{year, rank}]`, best first) and `average_rank`; `/profile/<id>/` carries the position, `average_rank`, every edition, `disciplines` (`[{name, position, places: [{year, rank}]}]`, `name` being the untranslated `Discipline.name`) and the badges (see Player badges); `/profiles/` rows carry neither. There is no teams-beaten share any more. The profile payloads carry names, teams and ranks only, never the username (the login name) or the email. Four organiser writes (`PATCH /game/<id>/score/`, `/result/<id>/value/`, `/discipline/<id>/reveal/`, `/round/<id>/close/`) carry `@permission_classes([IsOrganiser])` from `permissions.py` (staff flag: 401 without a token, 403 for a player) and refuse with 409 any row outside `latest_edition()` (the active edition with the highest year, `models/Edition.py`). They go through the models' `save()`, so scoring recomputes league points and closing a round schedules the next Swiss one; a round closes only once every game is played. A result value is settable only on a discipline without rounds (game points are computed); a time is sent as `mm:ss` and stored as `00:mm:ss` (minutes above 59 roll into hours). The sheet overwrites a game's score: a game is scored either from the site or through game events (unused today, additive), never both. Per-view policy decorators must go below `@api_view`: stacked above it DRF used to ignore them silently, and DRF 3.16+ raises a `TypeError` at import, so the wrong order stops the server from booting. `test_routes.py` fails when a view routed from `urls.py` lacks `@api_view` or its parameters differ from the route's converter names (each a 500 on every call). Tokens are issued at `/auth/token/` and auto-created per user by `signals.py`. `/auth/token/` is the only throttled API view (`ThrottledObtainAuthToken` in `views.py`: DRF's stock view with `LoginRateThrottle` from `throttling.py`; no `DEFAULT_THROTTLE_CLASSES`): `LOGIN_THROTTLE_RATE` (config, default `5/min`) attempts per client IP, every attempt counting, failed or not, and a token exempting no one, then a 429 with `Retry-After`. The IP is DRF's `get_ident` under `NUM_PROXIES` (config, default `1`): the last `X-Forwarded-For` entry, appended by nginx for a direct call and set by the front's login action for a login through the site (it calls the API server-side, so Django would otherwise see the front container for every visitor), else `REMOTE_ADDR`; an IPv6 client counts by its /64 and `::ffff:a.b.c.d` as its IPv4 (`client_key`). That is only sound while nothing reaches Django or the front except through nginx, and while every nginx location proxying to them sets `X-Forwarded-For` (`$proxy_add_x_forwarded_for`): otherwise the client picks the last entry. `docker-compose.prod.example.yml` therefore publishes the app ports on `127.0.0.1` only, nginx reaching them by service name. The counts live in the Django cache, a `FileBasedCache` in the temp dir so every gunicorn worker of the container shares them (the local-memory default is per process); `test_auth_token.py` and `test_admin_login.py` swap in a private local-memory cache and clear it in `setUp`. The Django admin login draws on the same per-IP bucket: `admin.py` sets `site.login_form` to `ThrottledAdminAuthenticationForm`, whose `clean()` runs `LoginRateThrottle` on every submitted form, failed or not (`get_ident` reads only `request.META`, so a plain Django request is identified like an API call), and past the limit re-renders the form (status 200) with a French `throttled` error before any password is checked. `LOGIN_THROTTLE_RATE` therefore bounds `/auth/token/` and `/admin/login/` together: attempts on either count against the other. Serializers are `fields="__all__"` `ModelSerializer`s with a few computed read-only fields.

**Summary endpoint:** public `GET /edition/year/<year>/summary/` (view `getEditionSummary`, `EditionSummarySerializer` and the `Summary*` serializers in `serializer.py`) returns the whole edition in one payload, active rows only: `edition`, `disciplines`, `teams` (each with its roster, whose players carry `id`, `user`, `first_name` and `last_name`, plus `ranking` and `total_points`), `results`, `rounds` (`id`, `discipline`, `order`, `is_over`) and `games` (`id`, `discipline`, `round`, `team1`, `team2`, `referees`, `is_played`, `score1`, `score2`). Together with `/editions/` and the two profile endpoints it is everything the front reads. `SummaryResultSerializer` nulls `ranking`, `points`, `time`, `points_difference` and `global_points` whenever the discipline's `reveal_score` is off or the result has no score for its type, so the public payload never leaks a score early (`TeamResult.ranking` itself returns 0 in those cases). `SummaryGameSerializer` follows the same rule but only for `score1`/`score2`: pairings, referee and `is_played` stay visible regardless of `reveal_score`. With a staff token (`context["staff"]` from `request.user.is_staff`) the game scores and the stored `points`/`time` of every result stay visible before the reveal, so an organiser can check and edit them; `ranking`, `points_difference` and `global_points` stay null for staff too until the discipline is revealed. Discipline rows carry `pairing_system` (`NO`, `RR`, `SW`). `games` excludes games of inactive rounds and is not filtered on the teams involved. The standings are computed once per request and passed through serializer context as `standings`; `SummaryResultSerializer` memoises them per edition for the single row the organiser score endpoints return and for the result views. `test_summary.py`, `test_organiser.py` and `test_reveal.py` pin the query counts (`SUMMARY_QUERIES`, `RESULT_PATCH_QUERIES`, `GAME_LIST_QUERIES`, `RESULT_LIST_QUERIES`), so a per-row fan-out fails the suite. In a manual edition `teams[].ranking` is the stored order (`null` for a team without one) and `teams[].total_points` is `null`; the front then hides the points figure (`rankedTeams` sorts a `null` rank last). `getTeamResultsByEdition` filters on `discipline__edition`.

The token-only game, round and result read views (`/game/<id>/`, `/games/...`, `/round/<id>/`, `/rounds/...`, `/result/<id>/`, `/results/...`) apply the same reveal rule with the same code: `GameSerializer` and `SummaryGameSerializer` share `RevealGameScoresMixin`, `TeamResultSerializer` subclasses `SummaryResultSerializer` (so a hidden `ranking` is `null` there too, not 0), and each view passes `context["staff"]`. They read through `_games()`, `_rounds()` and `_results()` in `views.py`, which leave out what the summary leaves out (games of an inactive round or discipline, rounds of an inactive discipline, results of an inactive discipline or team): the lists skip such a row and the detail views 404 on it. A player token gets null scores until the reveal (`test_reveal.py`).

**Player profiles:** `olympic_warriors/profiles.py` builds every person's record from the edition standings and stores nothing (spec under `docs/superpowers/specs/`). A person is a `User` with an active `Player` in an active edition, one participation per (user, edition): the lowest id among the rows with a valid team (active, of the player's edition), else the lowest id. An edition is finished once its `end_date` is before today in Europe/Paris (`paris_today()`: the server clock runs in UTC), and only a finished edition gives a rank, the team's standing (`final_rank` in a hand-ranked edition), so unfinished editions skip `compute_standings`; a computed edition in which no result has a rank gives no rank at all, since every team would otherwise tie 1st on nothing. A participation counts (`Participation.counts`) when finished, ranked and in an edition of at least two teams, and only then carries its team's ranked discipline results (`Participation.disciplines`, `DisciplinePlace(name, year, rank)`); `PlayerRecord.disciplines` groups them by discipline name (`_discipline_places`: places best first, disciplines in medal-table order with the name as tie-break, shared `position`s through `_positioned`, so the best disciplines are the ones at position 1); its `places` are the counted ranks best first (equal ranks newest first); `average_rank` (the mean rank, one decimal) averages the counted ones and is shown on the leaderboard rows and the profile, never used for the order. `participations()` (helpers `_one_row_per_edition`, `_is_ranked`) builds them and `leaderboard()` (helper `_place`, key `_medal_key` over a sequence of ranks, best first, plus an infinite sentinel, wrapped by `_places_key`) ranks people like a medal table on their places: more 1st places first, then more 2nd places, and so on, an extra lower place counting in a person's favour; identical places share a position and are listed by accent-insensitive name, the average rank plays no part, and people with nothing counted follow by name with a null position; it filters players by the loaded active editions and runs `2 + 3 × finished editions with players` queries (`PROFILES_QUERIES` in `test_profiles.py`). `Player.clean()` refuses a team of another edition and a second active row for the same (user, edition), both errors collected and raised together on `team`, the one field every admin form of a player has (an error on a field the form lacks makes Django raise `ValueError`); `PlayerAdmin` edits `team` from the changelist (`list_select_related`), with teams labelled `name (year)`. Django validates every row of a posted changelist page, so one duplicate pair blocks saving that whole page until one of its rows is deactivated. On the team page, `PlayerInlineForm` repeats `team` errors among the row errors, because the inline's hidden foreign key never shows its own; the team check reads `self.team` (not `team_id`), so on the TeamAdmin add page an unsaved new team, which already carries its edition, is checked too. Two new inline rows for the same person saved together both pass (the duplicate check only sees saved rows).

**Player badges:** `olympic_warriors/badges.py` computes the badges and the `Badge` table (migration `0033`) stores them (spec and catalogue under `docs/superpowers/specs/`). `earned(today)` builds a `History` from `profiles._load`/`_participations`, so the badges and the profiles never disagree on who played where, then runs the `RULES` over it; the discipline rules read each edition's `Standings.disciplines_of` data (the per-discipline ranking the profiles' « Par épreuve » uses, carrying the result type and points for the photo finish), so they cost no query, and the game rules add two (the sequence's active played games of active rounds of active disciplines, its blindtest guesses), so `BADGES_QUERIES` in `test_badges.py` is 4 + 3 per sequence edition when the sequence is not empty, and just `_load`'s 2 when it is. The **sequence** is the finished active editions with at least one active player, by year: a calendar year without an edition and an edition without any roster never break a streak, an edition the person missed does, an edition where they have no rank (no team, nothing ranked) breaks every place streak but no attendance streak (`reign` breaks only on the table after an edition where no participation counts), and an unfinished edition is not in it yet. **Earned at**: each rule walks the sequence and a badge is earned at the edition that completes it (`Badge.edition`, once for a one-time badge, at every new occurrence for a repeatable one), so playing more never takes a badge away; only a correction of past data can. The rule groups: edition places (a last place needs every active team ranked, at least 4 teams and a worst rank of 4th or below, so it is never a podium), streaks and career, loyalty (a participation is enough, no rank), teammates (`comrades` once per partner, both ways), the hall of fame (the `/players` table replayed with `_record`/`_place` after each sequence edition, from the first one by which two sequence editions have counted participations), disciplines and gods (a `ResultStanding.ranking` of 1 or 1 to 3, so revealed results only, disciplines matched across editions by name) and games (revealed disciplines only, except the refereeing count of `golden-whistle`, which counts a game only when the referee team is neither of the two playing: the schedulers leave a playing team in that slot as a placeholder, team1 in every Swiss round). `Badge.Codes` is the catalogue in display order (63 codes); `tier` is 0, or 1 to 3 for a tiered badge; `discipline` holds the database name for `specialist`, `unbeaten`, `perfect-run` and `steamroller` (judged discipline by discipline, so raw scores never compare across sports and one edition can give several to one person), `partner` the other person of `comrades`; `note` is an organiser memo, never served. `MANUAL_CODES` are the six given by hand (`mvp`, `fair-play`, `hype`, `costume`, `wounded`, `torchbearer`): `BadgeAdmin` (filters `code`, `edition`, `is_manual`, `is_active`; search by name) offers only those, and adding sets `is_manual`; a computed row is read-only except `is_active`, which revokes it, and cannot be deleted (the next refresh would recreate it: `has_delete_permission` is false for it on the Badge admin's own pages, not on a user's or an edition's delete page, which cascades to their badges, and `delete_selected`, overridden by name, and `delete_queryset` keep only the selection's manual rows); the changelist shows « Dernier calcul des badges » from `BadgeRefresh.refreshed_at` in Paris time (template `templates/admin/olympic_warriors/badge/change_list.html`). `refresh(today)` stores `earned()` in one transaction under the row lock of the one-row `BadgeRefresh` (`get_or_create` then `select_for_update`, so a cron run and an admin action run one after the other): it reads the computed rows of active editions only, deletes those no longer earned, active or not, and any duplicate of a key but one (an inactive one first, so a revocation survives, else the lowest id), `bulk_create`s the new ones, and leaves the others alone, so `created_at` and a revoked row's `is_active` survive; an inactive edition earns nothing but keeps its rows, hidden from the profiles, and gets them back unchanged when reactivated; manual rows are never read or written; it stamps `BadgeRefresh.refreshed_at` and returns `RefreshReport(added, removed, kept, refreshed_at)`, and a second run writes nothing. The partial unique constraint `badge_unique_computed` covers the computed rows, but Django 4.2 has no `nulls_distinct`, so rows without a partner stay unique through the diff. `refresh()` has three callers and no page view writes: the `refresh_badges` command (prints the counts and `refreshed_at`), run nightly by a crontab entry on the production host, `0 2 * * * cd <repo> && docker compose -f <compose file> exec -T server python manage.py refresh_badges >> /var/log/olympic-warriors-badges.log 2>&1` (host clock in UTC; 02:00 UTC is always after midnight in Paris, so an edition that ended the day before counts as finished; `-T` because cron has no terminal; a comment on the `server` service of `docker-compose.prod.example.yml` repeats it); the Edition changelist action « Recalculer les badges (toutes les éditions) », which needs the change permission on Edition, reports the counts and the refresh time in Paris, and whose selection does not matter since streaks and tables span editions; and a real `import_edition` (not `--dry-run`), after its transaction has committed: if the refresh then fails, the import stays and the command says so on stderr and exits with a `CommandError`. Without the cron entry a finished edition's badges wait for the action or an import. `FAMILIES` (discipline name to god; `GODS`, the nine in catalogue order, earn `olympus` together) and `KINDS` (mind or physical, for `brains-and-brawn`; `MINDS`, derived from `FAMILIES`, is the Athena disciplines plus Blindtest, and Fair is neither) match on discipline names, so renaming a discipline breaks them too. `GET /profile/<id>/` carries `badges` from `profile_badges(user_id)`, one query more than `/profiles/`: the active rows of active editions grouped by `(code, discipline, partner)` in catalogue order, each `{code, tier, years, discipline, partner}` with the highest tier, the years oldest first, the discipline's database name or `null`, and the partner as `{id, first_name, last_name}` or `null`; never `note`, `is_manual` or `created_at`. Tests: `test_badges.py` (every rule through `earned()` on small histories built by `World`, whose hand-ranked editions seat a teamless spectator so an edition everyone in the test missed stays in the sequence; the `FAMILIES`/`KINDS` coverage of every `Discipline` subclass; `BADGES_QUERIES`), `test_badge_refresh.py` (`refresh()`, the command, `BadgeAdmin`, the Edition action, the import hook) and the badge tests of `test_profiles.py` (the payload).

**Soft deletes:** nearly every model has `is_active`; the admin injects `is_active__exact=1` into every changelist via `request_only_active`, so inactive rows are hidden but still exist.

Settings: `olympic_warriors/config.py` (pydantic-settings) reads `ENV` and loads `DevConfig`/`ProdConfig`; any other value silently yields an empty config. `DATABASE_URL` wins over the `DB_*` vars. Media is served by Django only when `ENV=dev`. `settings.py` creates the `LOG_FILE` folder (`server/logs/`, gitignored) at import, so a fresh clone needs no `mkdir`. `Dockerfile.prod`/`Dockerfile.stage` run `collectstatic` with `ENV=prod`, so their build context needs `prod.env` (at least `SECRET_KEY`, `DEBUG`, `DB_*`) and no `dev.env`.

Known dead code: `olympic_warriors/models.py` (shadowed by the `models/` package) and the unused `bootstrap5`/`crispy_forms` apps. `olympic_warriors/templates/` holds only the Badge changelist override.

## Frontend architecture

**Every edition page is under a year segment.** `front/src/params/year.js` matches exactly four digits, so `[year=year]` never swallows `/login`: the routes are `/<year>` (hub), `/<year>/ranking` (the one list of teams: podium, rosters, points, with the discipline rail under the title), `/<year>/disciplines`, `/<year>/disciplines/<id>`, `/<year>/teams/<id>`; `/<year>/teams` is a `+page.server.js`-only 302 to that year's ranking, kept for old links since the teams grid merged into the ranking. `/` renders the latest edition's hub through the same `front/src/lib/components/EditionHub.svelte` as `/<year>`, without redirecting. The bare `/ranking`, `/teams` and `/disciplines` are `+page.server.js`-only 302 redirects to the latest year (`/teams` straight to its ranking). Detail routes take a numeric id, not a slug. Two routes sit outside the year segment because they span editions: `/players`, the all-time leaderboard from `/profiles/`, and `/players/<user id>`, a profile from `/profile/<id>/`, whose `+page.server.js` answers 404 before calling the API unless the id is canonical (1 to 10 digits, no leading zero); `src/lib/players.js` holds their helpers (`formatAverage` for the average rank on both pages, `editionStatus`, `fullName`, `bestDisciplines` (the position-1 disciplines, at most 3 plus a count), `byDisplayedName` (re-sorts tied disciplines by the name the page displays, so French pages sort French names), `spokenPlaces` (the hidden sentence both pages read out), and `shownPlaces` capping a leaderboard row at `MAX_PLACES = 8` places plus `+N`; each row's places and average are `aria-hidden` behind a visually hidden sentence such as `1st place in 2024, 2nd place in 2026, average rank 1.5`, and the average's label is « classement moyen » / `avg rank`, shortened to « moy. » / `avg` below 480px) and `src/lib/fixtures/players.js` holds their payloads. The profile pairs the average-rank card with an « Épreuve fétiche » / "Signature event(s)" card (the best disciplines' icons and names, at most 3 then `+N`, `—` without any) and, after « Éditions », shows a « Par épreuve » / "By discipline" section, one row per discipline (icon, name, places as a coloured rank and its year, `aria-hidden` behind a spoken sentence), absent when there is none. All read pages are public — no route checks a cookie.

Data flow: the root `+layout.server.js` fetches `/editions/` (sorted newest first) and exposes `editions` and `latestYear`; the `[year=year]/+layout.server.js` fetches `/edition/year/<year>/summary/` **once** and every page below reads `summary` from `parent()` or `data` rather than fetching again. The two detail pages use a universal `+page.js` that resolves the id inside that summary and throws 404 when it is missing. Every derivation is a pure function in `front/src/lib/edition.js` — `rankedTeams`, `disciplineResults`, `teamResults`, `findTeam`, `findDiscipline`, `editionPhase`, `countdownParts`, `startInstant` (the event starts at 09:00 Europe/Paris whatever the renderer's timezone), `formatDateRange`, `formatDifference`, `switchYearPath`, `disciplineSchedule`, `teamGames` — so they are unit-testable with no Svelte or network. The discipline detail page renders `disciplineSchedule` as a "Schedule" section by round below the ranking, and the team detail page renders `teamGames` as a "Games" section holding only the games the team played (refereeing duties are not listed).

API and errors: `front/src/lib/api.js` (`apiGet`/`apiPost`) throws a SvelteKit `error(status, message)` on any non-2xx or network failure, so loaders do not check return values; `front/src/lib/server/urls.js` prefixes `API_URL` (`$env/static/private`, baked in at build time, server-only). `front/src/routes/+error.svelte` renders thrown errors inside the layout; `front/src/error.html` is the static fallback for when the root layout itself fails (e.g. the API is down).

Presentation: `front/src/lib/icons.js` maps a discipline name to an SVG in `front/src/lib/img/icons/` — the file stem is the name lowercased with spaces and apostrophes removed — and falls back to `default.svg`, so a new discipline shows the fallback star until an icon is added; `src/lib/icons.test.js` lists every discipline model and fails when one has no icon. Badges: `src/lib/badges.js` is the front catalogue, `BADGES` mapping each code to its metal (`gold`, `silver`, `bronze`, `plain` for `--accent`) or to `tiers` (tier 1 bronze, 2 silver, 3 gold), in `Badge.Codes` order and mirrored by `BADGE_CODES` in `badges.test.js`, which fails when a code lacks a glyph, a metal, or a name or rule in either dictionary (`badge.<code>.name`/`.rule`); its helpers are `badgeGlyph` (`specialist` borrows its discipline's icon through `iconFor`, an unknown code gets `default.svg`), `badgeTier` (clamped to 1–3, so the metal, the pips and « Niveau n » always agree), `badgeMetal`, `badgeDetail` (the parts of a tile's detail line: the translated discipline first when there is one, then « Niveau 2 » and the year it was reached for a tiered badge, the year for `comrades`, `×2` and the years for a badge earned more than once) and `isKnownBadge` (a code from a newer server is left out). The 62 glyphs are `src/lib/img/badges/<code>.svg`, in the icons' house style (2000×2000 viewBox, white round-capped strokes, small parts filled) with no background and no frame, since `Badge.svelte` draws the ring: an `aria-hidden` medallion sized by `--badge-size` (as `MedalRank` by `--medal-size`), a ring in the metal colour with a hairline inner ring at 35%, the glyph at 60%, and three pips under a tiered badge, the first `tier` lit and the rest `--line` (an untiered badge keeps the empty pip row, so the names of a tile grid line up). The profile's « Badges » section (`/players/<id>`, between the counts line and the Editions, left out when empty) is a grid of tiles, each the medallion at 56px, the name, the detail line (for `comrades`, « avec » and a link to the partner's profile first) joined by ` · ` separators hidden from screen readers, and the rule, so nothing hides behind a hover. `components/Badge.test.js` pins the metals, the pips and `aria-hidden`; the profile's `page.test.js` pins the tiles, the partner link, the absent section and a French rendering. The site favicon is the header logo: `front/static/favicon.svg` is `src/lib/img/logo.svg` in a square viewBox, with `favicon.png` (32px, transparent) and `apple-touch-icon.png` (180px on `--bg`) rendered from it, so a logo change means regenerating all three; `app.html` links them through `%sveltekit.assets%`, `error.html` by root path (SvelteKit substitutes only the status and error message there).

**One dark theme, "Scoreboard"** (design spec under `docs/superpowers/specs/`), driven by the tokens on `:root` in `front/src/routes/styles.css`: surfaces (`--bg`, `--bg-raised`, `--bg-sunken`), rules (`--line`, `--line-strong`), a text ramp (`--ink`, `--text`, `--muted`, `--faint`, `--ghost`), `--accent`, medals (`--gold`, `--silver`, `--bronze`), outcomes (`--win`, `--loss`, `--todo`), the two font stacks, radii, `--page` (the content column every inner page wraps in a `.page` div) and `--tabbar`. Pages use tokens only — no hard-coded colour, no theme class, nothing to switch. Bebas Neue (display: headings, numbers, nav) and Inter (body) are **self-hosted** woff2 files in `front/static/fonts/` with `@font-face` and `font-display: swap`, the three hot weights (Bebas 400, Inter 400 and 600) preloaded in `app.html`, so there is no third-party font request. Uppercase is always `text-transform` in CSS: the markup stays sentence case and keeps its accents, so accessible names and test text read `Round 1`, `Ranking` in English and `Tour 1`, `Classement` in French. Utilities: `.label` (Inter 600, tracked, uppercased, muted), `.num` (display face, tabular figures, for figures and their unit such as `33 pts`, never for prose), `.dimmed` (`opacity: 0.35`, plus `pointer-events: none` on a link) for something not reachable yet, and `.visually-hidden`. An unrevealed discipline stays an ordinary link everywhere, because its page still shows the pairings: the disciplines card carries `.unrevealed` and dims its icon alone, and the `DisciplineRail` tile carries the same class and dims whole, with no `aria-disabled`. A global `prefers-reduced-motion` block cuts every transition and animation to `0.01ms`, so the hover lifts stay off for visitors who ask for it.

Shared pieces live in `front/src/lib/components/` and are imported by explicit path: `Header` (logo, year `<select>` through `switchYearPath`, which sends a team page to the other year's ranking, the Ranking, Disciplines and Players tabs with `aria-current`, Players pointing to `/players` whatever the year, plus a Photos tab when the edition has a `photos_url`; tabs hidden at 999px and below), `TabBar` (props `year`, `pathname`, `photosUrl`; the fixed bottom bar on phones with the same items, active item by href prefix and Ranking also lit on `/teams/<id>`, renders nothing without a year, hidden from 1000px up), `Breadcrumb` (`items: [{label, href?}]`, last item never a link), `MedalRank` (props `rank`, `ordinal`; `gold`/`silver`/`bronze`/`none` by rank, `—` for null, and it sizes itself from `--medal-size` set on the row around it, so pages scale the glyph without reaching into its scoped styles), `GameRow` (a game line: two teams, score, referee; with `roundLabel` and `highlightId` + `team1Id`/`team2Id` the team page reuses it, the own team in accent as plain text) and `EditionHub` (the hub: an `.actions` block with the ranking button once started and a Players link in both phases, outlined beside the ranking button and filled on its own before the start, since on a phone the hub has no tab bar). Roster names link to `/players/<user>` on the team page only: each team card of the ranking page is already one link, and links cannot nest. `+layout.svelte` is the only place route ids are read: it renders `TabBar` and puts `has-tabbar` on `.app` — the bottom padding — on every route except the hub (`/`, `/[year=year]`) and `/login`.

**Two languages, French first.** Every visible string goes through `t` from `front/src/lib/i18n/`: `fr.js` is the reference dictionary, `en.js` mirrors it key for key (`parity.test.js` fails otherwise), counting messages are `{ one, other }` picked with `Intl.PluralRules` (French puts 0 in the singular: `0 match`), and `disciplines.js` maps database discipline names to French (`icons.test.js` fails when a model is in neither `FRENCH_NAMES` nor `SAME_IN_FRENCH`). The locale comes from the `lang` cookie: the root `+layout.server.js` reads it through `localeFrom` (anything but `en` is `fr`), `+layout.svelte` puts it in Svelte context under `I18N`, and components call `useT()` / `useLocale()` at init only (Svelte's `getContext` throws anywhere else). `hooks.server.js` sets `<html lang>` from the same cookie and `Vary: Cookie`. The header's `FR | EN` form posts to `/lang`, whose action stores the cookie for a year and 303-redirects to the local path it was given, so the page reloads fully in the new language and no client code decides it (never `use:enhance` that form). Helpers in `edition.js` carry no language: `formatDateRange` and `ordinal` take the locale as last argument (`1er octobre`, `1re`, `2e` in French; anything but `en` is French), `disciplineSubtitle`/`roundCount` return counts the pages word, and an unknown team name is `null` (`GameRow` and the discipline page print `team.unknown`). `+error.svelte` words a 404 as `error.notFound` and every other error as `error.generic` outside dev, since thrown messages are English by construction; `error.html` is served before any layout and carries both languages. To move to Paraglide or svelte-i18n later: the flat key files convert directly, every call site is a `t(key, params)` and the locale is resolved in one place.

Page tests assert on text shapes, not on classes: `1 Bisons 5 pts` for a ranking row, `R1 Bisons 12 : 9 Aigles` for a team game row, `1 Léa Martin 1 2` then the figure `1.5` for a leaderboard row (its link named `1 Léa Martin 1st place in 2024, 2nd place in 2026, average rank 1.5`), `Relay 1 2026 2 2023` for a profile's by-discipline row, `2026 MxM 2 / 6` for a profile edition row, `Clean sweep ×2 · 2023 · 2026 Win three disciplines or more in one edition` for a profile badge tile. Changing the markup of a row or tile means updating those assertions in the same commit. Component and page tests render through `renderWith(Component, props, locale, organiser)` from `src/lib/test-utils.js`, English by default so the text-shape assertions read as before; a plain `render()` gets no context and therefore French. The fourth argument opts into the organiser view; `summaryStaff` in `front/src/lib/fixtures/summary.js` is the staff payload fixture (hidden Darts and Crossfit without rounds, Orienteering as Swiss). Tests of pages or components that use `use:enhance` stub it with `vi.mock('$app/forms', () => ({ enhance: () => ({ destroy() {} }) }))`, and the discipline page tests build their data with `dataFor(summary, id, editable)`. Every translated surface keeps one French test.

Auth: the login form action posts to `/auth/token/` (with the visitor's `getClientAddress()` as `X-Forwarded-For`, dropped when adapter-node throws, which it does when `ADDRESS_HEADER` names a header the request lacks; a 429 comes back as `throttled` and reads `login.throttled`) and stores the bare DRF token in the `token` cookie (httpOnly, SameSite lax, one week; `$lib/session.js` holds the name and options); `/logout` deletes it. The root `+layout.server.js` resolves `organiser` once per request by calling `/user/current/` with the token (`is_staff`; a 401/403 drops the cookie, an API failure keeps it and counts as a visitor), `+layout.svelte` puts it in context under `ORGANISER` (`useOrganiser()`, init only), and the `[year=year]` layout sends the token to the summary fetch only for an organiser and returns `editable` (organiser on the latest year). The header's pill slot holds a `Connexion` link to `/login` for a visitor and the `ORGA` logout pill for an organiser; at phone width the four top-bar controls (logo, year, that slot, `FR | EN`) tighten their padding so nothing overflows. There is no register form and there are no Svelte stores.

**Organiser tools** render only when `data.editable`, on the discipline page, through named form actions in `disciplines/[id]/+page.server.js` (`score`, `result`, `reveal`, `close`) that read the token cookie, call `apiPatch` and return `fail(status, {action, id, error})` with a dictionary key, or `{ok, action, id}`; the actions refuse a non-positive id, an empty or negative score and a negative points value with `orga.error.invalid` before calling the API; `use:enhance` re-runs the loads on success so the page shows the new state. `StaffBar` (hidden/public, the missing count, reveal or hide), `ScoreSheet` (a bottom sheet under 1000px, a centred dialog above: steppers, the `played` switch on by default, cancel/save, closes on success), result lines for a discipline without rounds (`disciplineEntries`, points or `mm:ss` time, empty clears), `GameRow`'s `onEdit` turning the pairing into a button, and `Clore le tour` on a complete Swiss round. Each result entry line is its own form and, like the score sheet, submits with `update({ reset: false })` so the shown value never lags the stored one; `dismissedForm` (set when the sheet closes) keeps a stale sheet error from reappearing on reopen. `Terminé`/`Done` on a closed round and the close button are organiser-only; visitors keep the plain game count. The time pattern allows at most three digits of minutes (`entryTime` renders `01:02:03` as `62:03`). The sheet focuses itself on phones and its first field from 1000px. An anonymous visitor gets no organiser control (times now print through `formatTime` for everyone). `formatTime` prints `mm:ss` with hours only when non-zero.

Tests sit next to what they cover (`src/lib/*.test.js` for the helpers, `page.test.js` beside a `+page.svelte`) and run on the fixtures in `front/src/lib/fixtures/summary.js`; `npm test` gates in CI, so keep them passing.
