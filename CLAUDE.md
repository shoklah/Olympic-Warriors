# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Olympic Warriors is a tool for running a multi-discipline sports event (rugby, dodgeball, blindtest, relay, etc.) across yearly "editions". Two deployable parts:

- `server/` — Django 4.2 + Django REST Framework API (single app `olympic_warriors`), PostgreSQL only (no sqlite fallback).
- `front/` — SvelteKit 2 / Svelte 4 (plain JS, no TypeScript; Vitest unit and component tests, no lint tooling) served via `adapter-node`.

`client/` is an empty leftover directory. `nginx/nginx.conf` is a dev-only config that no compose file references; production nginx config lives on the host under `nginx/user_conf.d` (not in the repo).

## Commands

Everything runs through the root `docker-compose.yml` (server on 3003, Postgres on **5433**, pgadmin on 5051, front on 5173). `server/docker-compose.yml` is a stale near-duplicate on port 5432; ignore it.

```bash
docker compose up --build              # migrate + runserver + vite dev
docker compose up -d -V --build front  # after a front dependency or Dockerfile change: node_modules is an anonymous volume, -V renews it
docker compose exec server python manage.py test                       # all Django tests (needs Postgres)
docker compose exec server python manage.py test olympic_warriors.tests.test_players.TestPlayersAPI.test_get_players
docker compose exec server python manage.py makemigrations
docker compose exec server python manage.py createsu                   # superuser from SU_USERNAME/SU_PASSWORD
docker compose exec server python manage.py create_tokens_for_users    # backfill DRF tokens
docker compose exec server python manage.py export_edition 2026 --out /server/edition-2026.json   # edition -> JSON without ids
docker compose exec server python manage.py import_edition /server/edition-2026.json --dry-run     # add --replace to overwrite that year
docker compose exec server python manage.py send_claim_links --dry-run   # who would be mailed a claim link (drop --dry-run to send)
docker compose exec server python manage.py refresh_badges             # rebuild the computed badges and their progress
docker compose exec server python manage.py refresh_badges --if-due    # the same, only when due (a host crontab runs it daily in prod)
docker compose exec server python manage.py refresh_badges --dry-run --verbose-rows   # list the badges a refresh would add (+) and remove (-), then roll back
pylint --load-plugins pylint_django --ignore=lib server/               # what CI runs (advisory, no .pylintrc)
```

Front (inside `front/`): `npm run dev`, `npm run build`, `npm run preview`. There is no `check` or `lint` script. `npm test` runs Vitest once over `src/**/*.test.js` (`vite.config.js`: jsdom, `src/setupTests.js` loading `@testing-library/jest-dom/vitest`, components rendered with `@testing-library/svelte`); summary fixtures live in `front/src/lib/fixtures/summary.js`.

Required env files, both gitignored:
- `server/dev.env` (copy `server/.env.example`); `ENV=prod` selects `server/prod.env`. Any real env var overrides the file and is parsed like it (`tests/test_config.py`). `ALLOWED_HOSTS` must include `server`, the hostname the front container uses, or every front page 400s. The file is read at startup: `docker compose restart server` after editing it.
- `front/.env` (copy `front/.env.example`) with `API_URL=http://server:3003` (in compose) or `http://localhost:3003`. `API_URL` is `$env/static/private`, so it is baked in at build time; a missing file fails the production build, and in dev `src/lib/server/urls.js` throws a clear error instead of fetching `undefined/...`. In production every front container must also get `ORIGIN=https://<public host>` (an adapter-node runtime variable, set in the compose file): SvelteKit's CSRF check compares the browser's `Origin` with it on every form POST (the `/lang` and `/theme` switches, login, logout, the organiser actions, the claim page and the profile owner's `photo`, `removePhoto` and `showcase` actions, the photo editor's multipart `fetch` included), so without it each one is refused with a 403 behind the TLS-terminating nginx; `docker-compose.prod.example.yml` sets it on `front` only, so a `front-stage` run from it refuses them all until it gets its own. It also needs `ADDRESS_HEADER=x-forwarded-for` for `getClientAddress()` to see the visitor rather than nginx, which the login and claim actions forward to the API's login throttle (`forwardedFor` in `$lib/server/forwarded-for.js`); set it only if the nginx location proxying to the front sets `X-Forwarded-For` (`$proxy_add_x_forwarded_for`), otherwise the header is the visitor's own and forgeable. Without it every login and claim through the site shares nginx's bucket. adapter-node's default `BODY_SIZE_LIMIT` (512K) is enough: the photo editor posts a 512px JPEG, far below it.

CI (`.github/workflows/test.yml`) has three jobs. `test` runs pylint with `continue-on-error`, so lint never fails it, then boots the compose stack, which fails it only when an image does not build or the stack does not start (nothing checks that the containers stay up). `server` (Python 3.11, a `postgres:16-alpine` service) installs `server/requirements.txt`, runs `makemigrations --check --dry-run` (a model change without its migration fails) and the whole Django suite, with no env file: `ENV=dev` and every required setting (`SECRET_KEY`, `DEBUG`, `DB_*`) come from job variables, so a new required config field needs a value there too. `front` (Node 22) runs `npm ci`, writes a throwaway `.env`, then `npm test` and `npm run build`. Any failing job fails the workflow: a missing migration, a failing Django or front test, a failing front build, or a compose stack that does not come up.

## Backend architecture

**Business logic lives in model `save()` overrides, not views, signals, or services.** Bulk operations (`bulk_create`, `queryset.update()`, `loaddata`) bypass all of it.

Domain: `Edition` owns `Team`s, `Player`s (wraps `auth.User` plus rating facets) and `Discipline`s. `Edition.year` is **unique** — it is the key the front routes and the export/import commands address an edition by, not the pk — and `Edition.photos_url` is an optional link to an external album (migration `0027`) that the front turns into a Photos tab. `Discipline.teams` is M2M through `TeamResult` (points or time, per `ResultTypes`). Team sports have `TeamSportRound`s of `Game`s; `GameEvent` subclasses (`RugbyEvent`, `DodgeballEvent`) log per-player actions and roll scores up into `Game.score*`, and `Game.save()` **recomputes** `TeamResult.points` for every team the game touches from the discipline's active, **played** games of active rounds (3 per win, 1 per draw), so score edits, flag flips, team swaps and soft deletes all resync and an unplayed game counts for nothing. `Game.is_played` is a manual boolean (default `False`, migration `0028` backfilled every existing game to `True`); the schedulers create games unplayed and `GameAdmin.list_editable` lets organisers flip it in the changelist. Points of disciplines without games are entered by hand and never recomputed. Rankings are never stored: `olympic_warriors/standings.py` computes an edition's whole standings in one pass (`compute_standings(edition)`: three queries, then discipline ranks gated by `Discipline.reveal_score`, points disciplines breaking ties on the points difference summed from active, played `Game` scores of active rounds, global points with the podium bonus among the discipline's active results of active teams, team totals and ranks). `Standings.disciplines_of(team_id)` returns a team's `DisciplineStanding`s (discipline id, name, standing, result type, stored points) in discipline id order from the same loaded rows, so it costs no query. `TeamResult.ranking`/`points_difference`/`global_points` and `Team.total_points`/`ranking` delegate to it, recomputing the edition on each access, so read many rows through `compute_standings` once, never through the properties in a loop (the older `TeamSerializer` list views still do, a known fan-out). Team totals sum the active disciplines only: a soft-deleted discipline drops out of them. `Team.final_rank` (migration `0031`, `list_editable` in `TeamAdmin`) records a finishing order by hand for an edition without result data: once any active team of an edition has one (`Edition.ranking_is_manual`), the team ranking is that order (`None` for a team without) and every `total_points` is `None`. `Discipline.get_ranking()` is a dead stub.

**Adding a discipline** (Django multi-table inheritance, `Discipline` is concrete):
1. `models/<Name>.py`: subclass `Discipline`, override `save()` to set `self.name` and `self.result_type` when `self.pk is None`, then call `super().save()`. See `models/Relay.py` for the minimal version, `models/Rugby.py` for one with a `GameEvent` subclass and scoring.
2. Export it from `models/__init__.py`.
3. `site.register(<Name>, DisciplineAdmin)` in `admin.py`.
4. `makemigrations` (each discipline gets its own table).
5. Add a matching SVG in `front/src/lib/img/icons/` — `iconFor()` in `front/src/lib/icons.js` derives the file stem from the discipline name, so a missing icon falls back to `default.svg`. Add the name to `DISCIPLINE_NAMES` in `front/src/lib/icons.test.js`, which fails until the icon exists **and** the name is in `FRENCH_NAMES` or `SAME_IN_FRENCH` in `front/src/lib/i18n/disciplines.js`.
6. Pick its god in `FAMILIES` in `server/olympic_warriors/badges.py`. Its kind in `KINDS` follows: mind under Athena, physical under any other god; add the name to `MINDS` for a mind discipline of another god (as Blindtest under Apollo), or exclude it from `KINDS` next to Fair when it is neither. `test_badges.py` fails when a `Discipline` subclass is missing from `FAMILIES` or, Fair aside, from `KINDS`.

The base `Discipline.save()` creates a `TeamResult` per active team on first save (`points` starts at `0` only for a points discipline with a pairing system, whose games compute it; a discipline without games and every `time` start at `None`, so "no result yet" is a null, never a zero, and switching a discipline to a pairing system later zeroes any null points before scheduling; `BlindtestGuess.save()` adds 1 per `is_artist_correct`/`is_song_correct` flipped on and takes it back when flipped off, onto that null-as-zero, in the result of its round's blindtest; a team created after the blindtest gets its result created on its first point, a guess for a team of another edition is refused on every save with a `ValidationError`, in the admin form through `clean()`) and dispatches scheduling by `pairing_system`, both on creation and when the pairing system is later set on a discipline with no round yet: round robin (`schedule/round_robin.py`, a full circle-method round robin up front with referee assignment, `max_rounds` defaulting to a single round robin) or Swiss (`schedule/swiss.py`, next round only, re-triggered when a `TeamSportRound.is_over` flips, `max_rounds` defaulting to log2 of the team count). The schedulers use `apps.get_model()` to avoid circular imports.

Discipline-specific admin and validation match on the discipline **name string** (`GameAdmin.get_inline_instances`, `RugbyEvent._discipline_validation`); renaming a discipline breaks scoring.

**Registration import:** saving an `Edition` with a new `registration_form` CSV runs `Edition.create_players_from_registration_form`, which delegates to `olympic_warriors/registration.py`. Columns are matched by stable fragments (the bracketed skill criterion such as `[Cardio]`, the prefix of the global-level question, `Prénom et Nom`, optional `Adresse e-mail`), so yearly wording changes need no code change. The skill set itself is versioned in `FORM_PROFILES` (`"2024"`: ten skills with `Observation et orientation` and a single `Endurance et cardio`; `"2025"`: the 2025/2026 set, also exported as `RATINGS`); `resolve_columns` returns the first profile whose criteria all match and `compute_ratings` weights with that profile's coefficients, so a form with a new skill set needs a new profile (each `id` at most 4 characters, the `PlayerRating.identifier` limit). The Edition row and the import share one transaction, returning players are linked by name-derived username (accents kept), the form email is stored when present, and both `Player` and `PlayerRating` rows are update-or-created so re-uploading a corrected form refreshes ratings without duplicates. `Player.rating` is the rounded global rating.

**Registration questionnaire** (spec `2026-10-04-in-app-registration-design.md`, slice 1): an edition's skills are data, `RegistrationSkill` (`name_fr`, `name_en`, `identifier`, `weight`, `order`, `is_active`; unique `(edition, identifier)`), seeded by migration `0042` (2024 from the 2024 profile, every later edition from the 2025 one, earlier ones nothing); `FORM_PROFILES` stays only for importing old CSVs. `registration.rate(skills, weights, global_level)` is the one rating formula (weights-averaged skills clipped to 1..10, ×2.5 when under 4 with a global answer above 4, blended `(weighted + 4 × global) / 5`, rounded to two decimals; `Player.rating` is its rounded value), shared by the CSV import and `questionnaire.recompute_ratings`. `Player` gains private per-edition answers: `global_level` (the raw global answer, stored because the blend cannot be inverted; null on editions imported before it), `dietary_restrictions`, `sport_frequency` (`SportFrequency`, the five answers of the form), `team_with` and `team_avoid` (who the player wishes to be with or to avoid, free text of at most 500 characters each, read by the organisers in the Player admin list, whose two columns are cut at 60 characters and whose `search_fields` cover them, and by the future team builder; the form's `PUT /registration/` takes and `GET` returns them, validated like the other free texts by `enrolment._text` under `MAX_TEAM = 500`, migration `0044`; `suggested` never carries them), `team_wishes` (the legacy combined text of the CSV registrations up to 2026, labelled « Souhaits d'équipe (ancien format) »: the CSV import still writes it, the API neither reads nor returns it and a re-registration never touches it, a body that still sends it has it ignored, and deactivation clears it), `attendance_confirmed` (the self-declared « payé et présent » tick), and `PlayerSport` rows (sport, level, practice, `duration_months`, `notes`; `notes` is a `TextField` with a 200-character validator so the import keeps a whole history); `level` is the highest level reached, an ordered ladder (`fun`, `informal`, `club`, `league`, `regional`) so exactly one answer is true, migration `0045` mapping the first version's `beginner`, `amateur`, `club`, `competition`. The CSV import fills `global_level`, frequency, wishes and the tick through `resolve_extras` (optional columns, matched by header fragment) and files the free-text sports answer as one `PlayerSport` row named « Historique (import) ». None of it is in a public payload (`PRIVATE_KEYS` in `test_showcase.py`), and `transfer.PRIVATE_FIELDS`/`NOT_EXPORTED` keep it out of `export_edition` (`global_level` travels; `RegistrationSkill` is exported). `Edition` gains `dates_confirmed` (default true): while it is false the hub shows « Dates à venir » instead of the date range and countdown and never offers the ranking, and `SummaryEditionSerializer` carries it. Admin: the Edition page edits `dates_confirmed` and the questionnaire through a `RegistrationSkill` inline whose `LockedSkillFormSet` refuses adding, deleting or re-identifying a skill once any player of the edition has a `PlayerRating` (`questionnaire.skills_locked`), plus the actions « Copier le questionnaire de l'édition précédente » (`copy_skills`) and « Recalculer les notes » (`recompute_ratings`, any edition, skipping players without a `global_level` or missing a skill and counting them); the Player admin shows the tick and a dietary column, filters on them and on frequency, and edits the sports inline. Known limit: the CSV import still weights skills with the `FORM_PROFILES` coefficients in code, not the `RegistrationSkill` weights, so after an organiser edits weights a re-import resets `Player.rating` until « Recalculer les notes » runs. Slice 3 built the pages (see « Registration on the front »). The two team fields are private like the other answers (`PRIVATE_KEYS`, `transfer.PRIVATE_FIELDS`, cleared by `accounts.deactivate`, left off the roster inline through `PlayerInline.exclude`). Deploying them: `migrate` (`0044_player_team_with_avoid`), then the server, then the front (an older front sending `team_wishes` has it dropped silently).

**In-app registration** (spec `2026-10-04-in-app-registration-design.md`, slice 2): `Edition.registration_opens`/`registration_closes`, FR/EN `registration_intro_*` and `skills_month_*`, `UserProfile.invited` (column, filter and editable in the profile list and change form, only for who holds `auth.change_user`, like the claim action: unticking revokes), `Player.withdrawn_at` and `LateRegistration` (`user`, `edition`, `granted_at`, `granted_by`, unique on user and edition, not exported). `registration_state.registration_state(edition, user)` is the one open/closed rule: closed `not_configured` without an active `RegistrationSkill` (a late pass does not bypass that) or without `registration_opens`, `not_yet_open`, `closed` once past `registration_closes` (inclusive; the day before `start_date` when blank, Paris dates); a holder of a `LateRegistration` is open (`late_pass`) through the edition's `end_date`. `claims.can_register(user)` is a person or an invited newcomer: `unclaimable_reason`, `unresettable_reason`, `complete_claim` and `views._not_an_account_owner` (`/me/email/`, `/me/password/`, `/me/deactivate/`) use it, `/me/photo/` and `/me/showcase/` stay for people, and `/me/` carries `can_register` from the profile row it already joins (`ME_QUERIES` unchanged). `GET`/`PUT`/`DELETE /registration/` (`myRegistration`, `IsAuthenticated`, in `test_permissions.py`'s `PLAYER` list, 404 `not_a_person` unless `can_register`, 404 `no_edition`, always the latest edition, `private, no-store`): GET returns the form (`enrolment.form_payload`: state with its reason, intro and month texts, skills, the active disciplines, the choice lists, the email as `{value, editable}`, the saved `registration` (kept, with `registered: false`, after a withdrawal) and `suggested` stable answers of the latest earlier registration while there is none); PUT validates (`enrolment.validate`, `{"errors": [codes]}` with `missing_rating`, `invalid_rating`, `invalid_global_level`, `missing_frequency`, `invalid_frequency`, `invalid_sport`, `too_many_sports`, `too_long`, `invalid_text`, `attendance_required`, `no_email`, `invalid_email`, `email_taken`), 409 `{"error": reason}` when closed or `removed_by_organiser` (an inactive Player with no `withdrawn_at`, unless a late pass), then `enrolment.save` in one transaction under the user's row lock (the Player created or reactivated with its team kept, ratings through `registration.rate` with the questionnaire weights, sports replaced as a set, the email saved only when the account had no usable one, an address at `olympicwarriors.com` or a subdomain counting as none: `emails.py` is the one definition, shared with the CSV import and `claim_mailing`); DELETE soft-deletes every active Player row of the person, sets `Player.withdrawn_at` and keeps the answers, 409 when closed and 409 `has_team` once a row has a real team (`profiles._valid_team`: active and of the edition; an organiser removes them). `RegistrationRateThrottle` (scope `registration`, `REGISTRATION_THROTTLE_RATE`, `30/hour` per user, PUT only, every PUT counting). `accounts.deactivate` now clears the private answers and deletes the `PlayerSport` rows. Admin: the Edition page edits the window and texts and shows « Inscription en ligne » (open, or why not, for an anonymous visitor); « Autoriser l'inscription tardive » on the Player and UserProfile lists grants a pass on the latest edition (`LateRegistration` admin lists and revokes); « Inviter des joueurs » (button on the profile list, `invitations.py`, needs `auth.add_user` and `auth.change_user`) takes one person or a paste of `Prénom Nom, email` lines: a real-email match is reused, else a username match is reused only when its email is a placeholder or equal, a username held by another real email, a staff or a deactivated account is a conflict (skipped, reported), an optional third column `identifiant` sets the username (two people sharing a name), a newcomer is created `invited`, a staff account is flagged invited with no link ever, and every other created or reused account gets a claim link in the admin's messages (a warning on one already activated: the link resets its password), optionally with a late pass; no `PUBLIC_URL` means nothing is created. Known limits: `email_taken` tells a logged-in player that an address has an account here (30 saves an hour per user), and it is checked then written with no uniqueness constraint, so two simultaneous registrations of one new address can both succeed (self-reset then switches off for both); a deactivated person keeps `invited` and any late pass, so a reactivation restores the right to register; the invite never writes an address onto a staff account.

**Team builder** (spec `2026-10-05-team-builder-design.md`, plan `2026-10-05-team-builder.md`; server half above, front half at its end): `TeamDraft` (`models/TeamDraft.py`, migration `0046_teamdraft`, one per edition, `related_name="team_draft"`, cascade-deleted with it, in `transfer.NOT_EXPORTED`) holds the organisers' working state as the browser keeps it, `document` = `{players_per_team, seed, links: [{player, kind: with|avoid, target}], teams: [{players}], locked}`, with `updated_by` and `updated_at` as the optimistic version (compared as its ISO string). `builder.py` holds all of it, with no views and no balancing (the generator and the scoring run in the browser): `validate_draft(document, player_ids)` returns the cleaned five keys or raises `DraftError(codes)` (`invalid_draft`, `unknown_player`, `bad_size` for a size outside 2 to 20, `too_many_links` above 200; ids must be active players of active users, none twice, locks a subset of the placed); `payload(edition)` is the roster with its private registration answers (`rating`, `global_level`, `ratings` by skill identifier, `sport_frequency`, `sports` as `{sport, level}`, `team_with`, `team_avoid`, `team` the id of a valid current team or null; never a username or email) plus `skills`, `registration_open` (`registration_state` without a user, so a late pass is ignored), `teams_exist` and the saved draft, in `BUILDER_QUERIES = 7` whatever the roster (`test_builder.py` pins it); `save_draft(edition, user, document, based_on)` stores under the row lock and raises `StaleDraft(current)` (current `None` when it was cleared) unless `based_on` is the stored `updated_at`; `apply(edition, based_on)` in one transaction under the edition's row lock refuses with `ApplyRefused(code, status)`: 409 `no_draft`, 409 `stale_draft`, 409 `teams_exist` (an active Team already exists), 400 `bad_size` (under two teams or sizes differing by more than one, checked before completeness) and 400 `incomplete` (the teams do not cover every active player exactly once); otherwise it creates « Équipe 1 »… in team order, sets `Player.team` through `save()`, backfills a `TeamResult` per new team in every active discipline through `Discipline.register_teams()` (which `Team.save()` never does), deletes the draft and returns `{teams: [{id, name, players}], unscheduled: [{id, name}]}`, `unscheduled` being the active disciplines with a pairing system and no active round (their results exist, their games are not scheduled). Three staff-only routes (`IsOrganiser` by default, not in `test_permissions.py`'s lists, `private, no-store`, the latest edition only: 404 `no_edition` for an unknown year, 409 `not_latest`): `GET /builder/<year>/` (`getBuilder`), `PUT`/`DELETE /builder/<year>/draft/` (`teamDraft`, body `{document, based_on}`, 400 `{"errors": [codes]}`, 409 `{"error": "stale_draft", "draft": {document, updated_at} | null}`, `DELETE` 204) and `POST /builder/<year>/apply/` (`applyTeams`, body `{based_on}`, the refusals above as `{"error": code}`). The Edition admin page shows « Constituer les équipes », a link to `<PUBLIC_URL>/<year>/builder` for the latest edition only and only with a usable `PUBLIC_URL`. Deploy: `migrate` (`0046`), server before front. **Front half**: route `/<year>/builder` (`routes/[year=year]/builder`, in `NO_TAB_BAR`): `+page.server.js` redirects a visitor to `/login?next=/<year>/builder`, lets the API's 403 reach a logged-in non-organiser, answers 404 for a year that is not the latest, loads `/builder/<year>/` with the token and sets `private, no-store`. The draft save and the apply are not form actions: the page `fetch`es its own JSON endpoints `builder/draft/+server.js` (`PUT`, `DELETE`) and `builder/apply/+server.js` (`POST`), thin forwards through `$lib/server/builder-proxy.js` (the token is an httpOnly cookie and `API_URL` is server-only, and the debounced saver and the stale check need the API's JSON answer, 409 body included, which a form action would flatten). The pure logic is in `$lib/builder/`: `names.js` (`splitNames`, `matchNames`: accent-insensitive whole name, unique first name, one-edit typo, ambiguous first names offering every candidate, never the player itself), `plan.js` (`teamSizes`, `emptyDraft`, `reconcile`: a saved draft against the current roster, departed players leave teams, links and locks, the others wait in the tray, `joined` counted only once teams exist), `score.js` (`features` with the fallbacks: a missing skill is the overall rating, a missing frequency `hour`, flagged `incomplete` for the « Profil incomplet » badge; `WEIGHTS`, whose order the tests pin, not the numbers, tuned by reading rather than by data; `makeScorer` giving the parts, the penalties and the `unmet` list), `generate.js` (`generate`: locked players stay, greedy snake placement then seeded swap improvement over restarts; `placeNewcomers`: the tray's players into the best-scoring smallest teams without moving anyone; `BuilderError` for fewer than two teams), `random.js` (seeded PRNG, `newSeed`) and `saver.js` (`createSaver`: debounced `PUT` based on the last returned version, a 409 stops it and hands the stored draft to `onStale`). The page keeps all state in `+page.svelte` (reloading the draft only when the load payload's identity changes, `loadedFrom`, since a bound child would otherwise re-run it) and drives three controlled panels in `$lib/components/builder/`: `BuilderRequests` (names to confirmed links), `BuilderTeams` (players per team, fixed once teams are proposed until « Tout réinitialiser », the tray, per-team stats and skill bars, drag and a move menu through `PlayerCard`, locks, the request notes switch remembered in `localStorage` as `builder.showRequests`) and `BuilderApply` (disabled while a player is unplaced, the draft is stale or unsaved or a request runs; a checkbox while registration is open; the server's refusal codes as `builder.error.*`; the `unscheduled` disciplines after success, and `invalidateAll()` so the layout sees the teams). An edition that already has teams shows only a message. The ranking page and the hub (`EditionHub`, a secondary action) link to the builder (`builder.link`) for an organiser of the latest edition while the edition has no team. The three panels share their progress block with the registration wizard through `StepProgress.svelte` (« Étape N sur 3 », the `role="progressbar"` bar and the step buttons, `canGo` for reachability, a `go` event), the builder adding free Previous/Next buttons. On a wide screen with a mouse the card's move menu is visually hidden (still focusable, shown on focus) because cards are dragged onto their team, and stays for touch and small screens; the name matcher (`$lib/builder/names.js`) scans each part of a wish for the players' first and last names as whole words instead of interpreting the sentence. Tests: `$lib/builder/*.test.js`, `routes/[year=year]/builder/` (`page.test.js`, `page.server.test.js`, `endpoints.test.js`), `components/builder/*.test.js` on the fixture `$lib/fixtures/builder.js`.

**Edition transfer:** `olympic_warriors/transfer.py` moves a whole edition between databases (local to prod). The export carries no database ids (users by username, rows cross-referenced by throwaway `_id`s, MTI children as `subclass`/`child`); the import inserts with `save_base(raw=True)` so no model `save()` side effect runs, reuses existing users by username and creates missing ones with a random password nobody receives (a person sets their own through a claim link, see Player accounts). Media files are not in the document; on prod, `mediafiles` is a docker volume, so copy them into the container (`docker compose cp`), not into the repo folder. Badges, their progress and profiles are not exported (`transfer.NOT_EXPORTED`: `Badge`, `BadgeRefresh`, `BadgeProgress`, and `UserProfile`, which is about a person rather than an edition and lives on prod only; `test_transfer.py` fails when a root model is neither exported nor listed there): a real `import_edition` rebuilds the computed ones and the progress with `badges.refresh()` once the import has committed, manual badges are not transferred, and `--replace` cascade-deletes the replaced edition's badges. The runbook is in the transfer design spec under `docs/superpowers/specs/`.

**API:** ~70 flat `@api_view` functions in `views.py` wired in one hand-written list in `urls.py` (no routers, no `/api/` prefix except the schema at `/api/schema/swagger/`). Authentication is DRF `TokenAuthentication`, and the API is **staff-only by default**: `DEFAULT_PERMISSION_CLASSES` is `IsOrganiser` from `permissions.py` (staff flag: 401 without a token, 403 for a player), so a view opens only through its own `@permission_classes` below `@api_view`. `AllowAny` makes it public: six edition/discipline read views, the two profile views (`GET /profiles/`, the leaderboard; `GET /profile/<user_id>/`, 404 for someone who never played), the discipline all-time table (`GET /discipline/<id>/all-time/`, see Player profiles), its index (`GET /disciplines/all-time/`) and the claim link (`GET`/`POST /claim/<uidb64>/<token>/`, see Player accounts); `/auth/token/` (DRF's `permission_classes = ()`) and the schema views (drf-spectacular's `SERVE_PERMISSIONS`) open themselves. `IsAuthenticated` opens it to any token, a player's included: the caller's own `/me/`, `/me/photo/` and `/me/showcase/`, and the reveal-aware game, round and result reads (below). There is no teams-beaten share any more. The public payloads carry names, teams, ranks, photos and showcases only, never the username (the login name), the email, `photo_locked`, `claimed_at` or the stored pins: only `/me/` carries the username, the email, `photo_locked` and the pins (`showcase.codes`), to their owner, and `test_showcase.py` walks `/profiles/`, two `/profile/<id>/`, a summary and a `/discipline/<id>/all-time/` for its `PRIVATE_KEYS` and the email, an anonymized person's included. Four organiser writes (`PATCH /game/<id>/score/`, `/result/<id>/value/`, `/discipline/<id>/reveal/`, `/round/<id>/close/`) still carry `@permission_classes([IsOrganiser])` explicitly and refuse with 409 any row outside `latest_edition()` (the active edition with the highest year, `models/Edition.py`). They go through the models' `save()`, so scoring recomputes league points and closing a round schedules the next Swiss one; a round closes only once every game is played. A result value is settable only on a discipline without rounds (game points are computed); a time is sent as `mm:ss` and stored as `00:mm:ss` (minutes above 59 roll into hours). The sheet overwrites a game's score: a game is scored either from the site or through game events (unused today, additive), never both. The password routes are public too, `AllowAny` with `@authentication_classes([])`: `POST /password-reset/` (`requestPasswordReset`, body `{email}`, always 200 `{}` whatever matched, an unparsable body included, a 429 only from the throttles) and `GET`/`POST /password-reset/<uidb64>/<token>/` (`resetPassword`, the claim view's contract through `_claim_response`, so the same identical 404 and validator codes, a new token on success; see Player accounts). Three more `/me/` writes are open to any token and answer 404 `not_a_person` to a non-person caller before reading the body (an organiser who plays is a person and is served: Hugo, 2026-10-03), each in `test_permissions.py`'s `PLAYER` list: `PUT /me/email/` (`myEmail`, JSON `{password, email}`: 400 `wrong_password`, 400 `invalid_email`, else `{email}`), `PUT /me/password/` (`myPassword`, `{current, new}`: 400 `wrong_password`, `{"errors": [codes]}` with the claim's validator codes, else a fresh `{token}` and every older session ends) and `POST /me/deactivate/` (`deactivateMe`, `{password}`, 204; a staff or superuser caller gets 400 `organiser_cannot_deactivate` before the password check, the same answer whatever the password, nothing changed); they share `PasswordCheckThrottle` (scope `password`, a `UserRateThrottle`, `PASSWORD_THROTTLE_RATE` config, default `10/hour` per user, every request counting, right password or not, so a stolen session cannot guess it) and read the body through `_account_body`, `@sensitive_variables` on each. `POST /password-reset/` draws on three throttles: the login bucket (`LoginRateThrottle`, per IP, shared with `/auth/token/`, a claim's POST and the admin login, so `LOGIN_THROTTLE_RATE` bounds them together with it) and `ResetEmailRateThrottle` (scope `reset_email`, `RESET_EMAIL_THROTTLE_RATE`, default `3/hour`, per lower-cased address, counted whether or not anyone has it so the 429 reveals nothing; a body without a usable email is not counted by it, the IP bucket still is); `test_auth_token.py`, `test_claims.py`, `test_me.py` and `test_permissions.py` already clear a private cache, so do the new account and reset tests. Per-view policy decorators must go below `@api_view`: stacked above it the pinned DRF 3.15 ignores them silently, so the view falls back to the staff-only default and locks out the visitors or players it was opened for (`test_permissions.py` catches it), and DRF 3.16+ raises a `TypeError` at import, so the wrong order stops the server from booting. `test_routes.py` fails when a view routed from `urls.py` lacks `@api_view` or its parameters differ from the route's converter names (each a 500 on every call). Tokens are issued at `/auth/token/`, auto-created per user by `signals.py` and replaced by a claim. Three kinds of call are throttled, with no `DEFAULT_THROTTLE_CLASSES` (a function view has one throttle list for all its methods, so the two per-method throttles check the method themselves). `/auth/token/` (`ThrottledObtainAuthToken` in `views.py`: DRF's stock view with `LoginRateThrottle` from `throttling.py`) and a claim link's POST (`ClaimRateThrottle`: `LoginRateThrottle` on POST only, the same scope and rate; the claim page's GET is free, since it answers only for a valid token and the page re-runs it after each refused POST) share the login bucket: `LOGIN_THROTTLE_RATE` (config, default `5/min`) attempts per client IP, every attempt counting, failed or not, a dead link's included, and a token exempting no one, then a 429 with `Retry-After`. A photo upload has its own: `PhotoRateThrottle`, a `UserRateThrottle` of scope `photo` on PUT only, `PHOTO_THROTTLE_RATE` (config, default `10/hour`) per user, every PUT counting, refused or not, and a DELETE never. The IP is DRF's `get_ident` under `NUM_PROXIES` (config, default `1`): the last `X-Forwarded-For` entry, appended by nginx for a direct call and set by the front's login and claim actions for a call through the site (they call the API server-side, so Django would otherwise see the front container for every visitor), else `REMOTE_ADDR`; an IPv6 client counts by its /64 and `::ffff:a.b.c.d` as its IPv4 (`client_key`). That is only sound while nothing reaches Django or the front except through nginx, and while every nginx location proxying to them sets `X-Forwarded-For` (`$proxy_add_x_forwarded_for`): otherwise the client picks the last entry. `docker-compose.prod.example.yml` therefore publishes the app ports on `127.0.0.1` only, nginx reaching them by service name. The counts live in the Django cache, a `FileBasedCache` in the temp dir so every gunicorn worker of the container shares them (the local-memory default is per process); `test_auth_token.py`, `test_admin_login.py`, `test_claims.py`, `test_me.py` and `test_permissions.py` swap in a private local-memory cache and clear it in `setUp`. The Django admin login draws on the same per-IP bucket: `admin.py` sets `site.login_form` to `ThrottledAdminAuthenticationForm`, whose `clean()` runs `LoginRateThrottle` on every submitted form, failed or not (`get_ident` reads only `request.META`, so a plain Django request is identified like an API call), and past the limit re-renders the form (status 200) with a French `throttled` error before any password is checked. `LOGIN_THROTTLE_RATE` therefore bounds `/auth/token/`, a claim link's POST and `/admin/login/` together: attempts on any of them count against the others. Serializers are `fields="__all__"` `ModelSerializer`s with a few computed read-only fields.

**Summary endpoint:** public `GET /edition/year/<year>/summary/` (view `getEditionSummary`, `EditionSummarySerializer` and the `Summary*` serializers in `serializer.py`) returns the whole edition in one payload, active rows only: `edition`, `disciplines`, `teams` (each with its roster, whose players carry `id`, `user`, `first_name`, `last_name` and `photo`, the small URL or `null` through `select_related("user__profile")` on the roster prefetch, so `SUMMARY_QUERIES` did not move, plus `ranking` and `total_points`), `results`, `rounds` (`id`, `discipline`, `order`, `is_over`) and `games` (`id`, `discipline`, `round`, `team1`, `team2`, `referees`, `is_played`, `score1`, `score2`). Together with `/editions/`, the two profile endpoints, the discipline all-time table and its index it is everything the front's pages read; besides them the root layout calls `/me/` for a request carrying a token, and the claim page and the profile owner's actions call the claim link and `/me/photo/` and `/me/showcase/`. `SummaryResultSerializer` nulls `ranking`, `points`, `time`, `points_difference` and `global_points` whenever the discipline's `reveal_score` is off or the result has no score for its type, so the public payload never leaks a score early (`TeamResult.ranking` itself returns 0 in those cases). `SummaryGameSerializer` follows the same rule but only for `score1`/`score2`: pairings, referee and `is_played` stay visible regardless of `reveal_score`. With a staff token (`context["staff"]` from `request.user.is_staff`) the game scores and the stored `points`/`time` of every result stay visible before the reveal, so an organiser can check and edit them; `ranking`, `points_difference` and `global_points` stay null for staff too until the discipline is revealed. Discipline rows carry `pairing_system` (`NO`, `RR`, `SW`). `games` excludes games of inactive rounds and is not filtered on the teams involved. The standings are computed once per request and passed through serializer context as `standings`; `SummaryResultSerializer` memoises them per edition for the single row the organiser score endpoints return and for the result views. `test_summary.py`, `test_organiser.py` and `test_reveal.py` pin the query counts (`SUMMARY_QUERIES`, `RESULT_PATCH_QUERIES`, `GAME_LIST_QUERIES`, `RESULT_LIST_QUERIES`), so a per-row fan-out fails the suite. In a manual edition `teams[].ranking` is the stored order (`null` for a team without one) and `teams[].total_points` is `null`; the front then hides the points figure (`rankedTeams` sorts a `null` rank last). `getTeamResultsByEdition` filters on `discipline__edition`.

The game, round and result read views (`/game/<id>/`, `/games/...`, `/round/<id>/`, `/rounds/...`, `/result/<id>/`, `/results/...`), the only reads besides `/me/` open to a player's token (`IsAuthenticated`), apply the same reveal rule with the same code: `GameSerializer` and `SummaryGameSerializer` share `RevealGameScoresMixin`, `TeamResultSerializer` subclasses `SummaryResultSerializer` (so a hidden `ranking` is `null` there too, not 0), and each view passes `context["staff"]`. They read through `_games()`, `_rounds()` and `_results()` in `views.py`, which leave out what the summary leaves out (games of an inactive round or discipline, rounds of an inactive discipline, results of an inactive discipline or team, and every row of an inactive edition, whose summary is a 404): the lists skip such a row and the detail views 404 on it. A player token gets null scores until the reveal (`test_reveal.py`), so these views carry nothing the public summary does not.

**Player profiles:** `olympic_warriors/profiles.py` builds every person's record from the edition standings and stores nothing (spec under `docs/superpowers/specs/`). A person is a `User` with an active `Player` in an active edition (the rows of `person_players()`, which `is_person(user)` and `person_ids()`, the people's sorted ids, ask in one query each, so the claim links, `/me/` and the showcase's rarity never compute the leaderboard to know who is a person; `test_showcase.py` checks `person_ids()` against it), one participation per (user, edition): the lowest id among the rows with a valid team (active, of the player's edition), else the lowest id. An edition is finished once its `end_date` is before today in Europe/Paris (`paris_today()`: the server clock runs in UTC), and only a finished edition gives a rank, the team's standing (`final_rank` in a hand-ranked edition), so unfinished editions skip `compute_standings`; a computed edition in which no result has a rank gives no rank at all, since every team would otherwise tie 1st on nothing. A participation counts (`Participation.counts`) when finished, ranked and in an edition of at least two teams. Whether it counts or not, a participation with a valid team carries its team's revealed, scored results in the edition's contested disciplines (those whose ranked results do not all share one rank, `_contested`: a lone scored result, or every team tied on 0 before a game is played, beats nobody; `Participation.disciplines`, `DisciplinePlace(name, year, rank, discipline_id)` from `_revealed_places`, shared with the all-time tables): `participations()` fills them for finished editions, and `profile_record(user_id)`, which `GET /profile/<id>/` uses in place of `leaderboard()`, adds the person's running editions (3 queries per running edition they have a team in), so « Par épreuve » and « Épreuve fétiche » move during an edition like the all-time tables while the position, places, average rank and badges wait for its end; `PlayerRecord.disciplines` groups them by discipline name (`_discipline_places`: places best first, disciplines in medal-table order with the name as tie-break, shared `position`s through `_positioned`, so the best disciplines are the ones at position 1); its `places` are the counted ranks best first (equal ranks newest first); `average_rank` (the mean rank, one decimal) averages the counted ones and is shown on the leaderboard rows and the profile, never used for the order. `participations()` (helpers `_one_row_per_edition`, `_is_ranked`) builds them and `leaderboard()` (helper `_place`, key `_medal_key` over a sequence of ranks, best first, plus an infinite sentinel, wrapped by `_places_key`) ranks people like a medal table on their places: more 1st places first, then more 2nd places, and so on, an extra lower place counting in a person's favour; identical places share a position and are listed by accent-insensitive name, the average rank plays no part, and people with nothing counted follow by name with a null position; it filters players by the loaded active editions and runs `2 + 3 × finished editions with players` queries (`LEADERBOARD_QUERIES` in `test_profiles.py`). `_load`'s players query joins each user's profile row (`select_related("user__profile", "team")`, a missing row cached as `None`), so a `PlayerRecord` also carries `photo` (`avatars.photo_urls`: `{large, small}` or `None`) and `pins` (the stored `UserProfile.showcase`, earned or not) at no query; every Player row of a person points at the same user, so whichever one stands for an edition, the profile is the same. The two endpoints add the badges and the rarity stats (see Player badges), `PROFILES_QUERIES = 4 + 3 ×` those editions, and `/profile/<id>/` adds one for the badge progress and `profile_record()`'s 3 per running edition the person has a team in. `discipline_table(name)` is a discipline's all-time table (spec `2026-09-24-discipline-all-time-table-design.md`): every revealed, scored result of that discipline name in an active edition, finished or running, where the discipline is contested (`_revealed_places`), credited to its team's roster (the person's one participation per edition, `_one_row_per_edition`), ordered by the same medal key on those places, ties sharing a position and listed by name, plus the `years` that give a place. It neither waits for the edition to end nor asks the edition or team to be ranked, the profile's rule for discipline places too, so a person's row matches their profile's « Par épreuve » row for that discipline; the leaderboard and the badges still count finished editions only. It has no date and loads its own data: the active editions holding the discipline, their players, then `compute_standings` of each with a player (`2 + 3 ×` those editions, one query when none holds it). The public `GET /discipline/<id>/all-time/` (view `getDisciplineAllTime`, 404 unless the discipline and its edition are active) looks up the id's name and serves `{name, years, players: [{id, first_name, last_name, position, places}]}`, the same table from any edition's discipline of that name, in one query more (`DISCIPLINE_TABLE_QUERIES`). Its index, `held_disciplines()` (one query), lists every `Discipline.name` an active edition held through an active row, finished or not, revealed or not, in accent-insensitive name order, a nameless row left out, each a `HeldDiscipline` with its `editions` (`HeldEdition(year, discipline_id)`, the lowest id of that year, oldest first); the public `GET /disciplines/all-time/` (view `getHeldDisciplines`) serves it as `[{name, editions: [{year, discipline}]}]` (`TestHeldDisciplines` in `test_profiles.py`). `Player.clean()` refuses a team of another edition and a second active row for the same (user, edition), both errors collected and raised together on `team`, the one field every admin form of a player has (an error on a field the form lacks makes Django raise `ValueError`); `PlayerAdmin` edits `team` from the changelist (`list_select_related`), with teams labelled `name (year)`. On the team page, `PlayerInlineForm` repeats `team` errors among the row errors, because the inline's hidden foreign key never shows its own; the team check reads `self.team` (not `team_id`), so on the TeamAdmin add page an unsaved new team, which already carries its edition, is checked too. Two new inline rows for the same person saved together both pass (the duplicate check only sees saved rows).

**Player badges:** `olympic_warriors/badges.py` computes the badges and the `Badge` table (migrations `0033`, `0034` and `0035_badge_master`) stores them (spec and catalogue under `docs/superpowers/specs/`). `compute(today)` builds a `History` from `profiles._load`/`_participations`, so the badges and the profiles never disagree on who played where, runs the rules over it (the hall of fame first, since it also hands back the reign runs, then the `RULES`) and returns the badges and the badge progress (see Badge progress); `earned(today)` is its badges alone; the discipline rules read each edition's `Standings.disciplines_of` data (the per-discipline ranking the profiles' « Par épreuve » uses, carrying the result type and points for the photo finish), so they cost no query, and the game rules add two (the sequence's active played games of active rounds of active disciplines, its blindtest guesses), so `BADGES_QUERIES` in `test_badges.py` is 4 + 3 per sequence edition when the sequence is not empty, and just `_load`'s 2 when it is. The **sequence** is the finished active editions with at least one active player, by year: a calendar year without an edition and an edition without any roster never break a streak, an edition the person missed does, an edition where they have no rank (no team, nothing ranked) breaks every place streak but no attendance streak (`reign` breaks only on the table after an edition where no participation counts), and an unfinished edition is not in it yet. **Earned at**: each rule walks the sequence and a badge is earned at the edition that completes it (`Badge.edition`, once for a one-time badge, at every new occurrence for a repeatable one), so playing more never takes a badge away; only a correction of past data or of the rules can. The one exception is `master` (spec under `docs/superpowers/specs/`), a title held, not earned for good: winning every edition of the sequence that ranked a discipline (matched by name; at least `MASTER_EDITIONS = 2`, each won by the person's team, a shared 1st included, a missed edition counting as not won; a hidden, unscored or uncontested one is skipped), earned at the second such edition and judged on the whole sequence (`_held`, `_masters`), so the next finished edition of it the person does not win takes it away and the refresh deletes the row. The rule groups: edition places (a last place needs every active team ranked, at least 4 teams and a worst rank of 4th or below, so it is never a podium), streaks and career, loyalty (a participation is enough, no rank), teammates (`comrades` once per partner, both ways), the hall of fame (the `/players` table replayed with `_record`/`_place` after each sequence edition, from the first one by which two sequence editions have counted participations, except that `goat` also reads the table after the first edition with counted participations, whose leader earns it, Hugo, 2026-10-04: that table is only the edition's ranking, so nothing else reads it), disciplines and gods (`master` included; a `ResultStanding.ranking` of 1 or 1 to 3, so revealed results only, in a contested discipline only: `_discipline_results` ranks 0 every result of a discipline outside `profiles._contested`, the rule of the profiles and the all-time tables, so a lone scored result or every team tied on 0 before a game gives no win, no podium and no ranked discipline for `metronome`, at no extra query; a podium counting for `metronome` and `decathlete` only in an edition of at least 4 teams, since in a smaller one every result is on it; disciplines matched across editions by name) and games (revealed disciplines, played games only, with no contested rule: an unplayed game counts for nothing and a played one has a real opponent, so `unbeaten` and `steamroller` stand even in a discipline where every team ties). `Badge.Codes` is the catalogue in display order (62 codes: `golden-whistle` and `globetrotter` were removed on 2026-09-24, migration `0034` deleting their rows, and `master` added after `specialist` the same day, migration `0035_badge_master`; `UserProfile.showcase` and `BadgeProgress.code` share the choices, so a catalogue change migrates all three fields, see Player accounts); `tier` is 0, or 1 to 3 for a tiered badge; `discipline` holds the database name for `specialist`, `master`, `unbeaten`, `perfect-run` and `steamroller` (judged discipline by discipline, so raw scores never compare across sports and one edition can give several to one person), `partner` the other person of `comrades`; `note` is an organiser memo, never served. `MANUAL_CODES` are the six given by hand (`mvp`, `fair-play`, `hype`, `costume`, `wounded`, `torchbearer`): `BadgeAdmin` (filters `code`, `edition`, `is_manual`, `is_active`; search by name) offers only those, and adding sets `is_manual`; a computed row is read-only except `is_active`, which revokes it, and cannot be deleted (the next refresh would recreate it: `has_delete_permission` is false for it on the Badge admin's own pages, not on a user's or an edition's delete page, which cascades to their badges, and `delete_selected`, overridden by name, and `delete_queryset` keep only the selection's manual rows); the changelist shows « Dernier calcul des badges » from `BadgeRefresh.refreshed_at` in Paris time (template `templates/admin/olympic_warriors/badge/change_list.html`). `refresh(today)` stores `compute()`'s badges (and its progress, see Badge progress) in one transaction under the row lock of the one-row `BadgeRefresh` (`get_or_create` then `select_for_update`, so a cron run and an admin action run one after the other): it reads the computed rows of active editions only, deletes those no longer earned, active or not, and any duplicate of a key but one (an inactive one first, so a revocation survives, else the lowest id), `bulk_create`s the new ones, and leaves the others alone, so `created_at` and a revoked row's `is_active` survive; an inactive edition earns nothing but keeps its rows, hidden from the profiles, and gets them back unchanged when reactivated; manual rows are never read or written; it stamps `BadgeRefresh.refreshed_at` and returns `RefreshReport(added, removed, kept, progress, refreshed_at)` (`progress` the progress rows created, updated or deleted), and a second run writes nothing. The partial unique constraint `badge_unique_computed` covers the computed rows, but Django 4.2 has no `nulls_distinct`, so rows without a partner stay unique through the diff. `refresh()` has three callers and no page view writes: the `refresh_badges` command (prints the counts, the progress rows written and `refreshed_at`), run daily with `--if-due` by a crontab entry on the production host (Hugo, 2026-09-24: editions are yearly, so a nightly full rebuild was wasted, hence monthly; Hugo, 2026-09-30: daily with `--if-due`, so badges and bars are fresh the morning after an edition and nothing is recomputed the rest of the year), `0 2 * * * cd <repo> && docker compose -f <compose file> exec -T server python manage.py refresh_badges --if-due >> $HOME/logs/olympic-warriors-badges.log 2>&1` (02:00 host time every day; `--if-due` refreshes only when `refresh_due(today)` says so and otherwise logs one « Nothing to refresh » line; the production host's clock runs in Europe/Paris, and 02:00 UTC would be after midnight in Paris too, so either way an edition that ended the day before counts as finished; `-T` because cron has no terminal; the log sits in the crontab user's home, `~/logs` created once, since that user cannot write `/var/log`; a comment on the `server` service of `docker-compose.prod.example.yml` repeats it); the Edition changelist action « Recalculer les badges (toutes les éditions) », which needs the change permission on Edition, reports the counts and the refresh time in Paris, and whose selection does not matter since streaks and tables span editions; and a real `import_edition` (not `--dry-run`), after its transaction has committed: if the refresh then fails, the import stays and the command says so on stderr and exits with a `CommandError`. Without the cron entry a finished edition's badges wait for the action or an import; with it, only the first morning after an edition refreshes (Hugo, 2026-09-30), so results revealed or corrected later, and a deactivated or reactivated edition (whose badges the profiles hide or show at once while its bars wait), wait for the action or the 30-day fallback: run the action once an edition's last results are in, and after deactivating or reactivating an edition. `FAMILIES` (discipline name to god; `GODS`, the nine in catalogue order, earn `olympus` together) and `KINDS` (mind or physical, for `brains-and-brawn`; `MINDS`, derived from `FAMILIES`, is the Athena disciplines plus Blindtest, and Fair is neither) match on discipline names, so renaming a discipline breaks them too. `GET /profile/<id>/` carries `badges` from `profile_badges(user_id)` (one query), and `badges_by_user(user_ids)` reads the same entries for every person of `/profiles/` in one (none for no id), both through `_shown_rows()` and `_grouped()`: the active rows of active editions grouped by `(code, discipline, partner)` in catalogue order, each `{code, tier, years, discipline, partner}` with the highest tier, the years oldest first, the discipline's database name or `null`, and the partner as `{id, first_name, last_name, photo}` (the small URL or `null`, `partner__profile` joined in) or `null`; never `note`, `is_manual` or `created_at`. With the rarity stats' query, both endpoints run `PROFILES_QUERIES`, the profile plus 1 for its progress and 3 per running edition the person has a team in (see Player profiles); `/profiles/` runs neither query when nobody is listed. Tests: `test_badges.py` (every rule through `earned()` on small histories built by `World`, whose hand-ranked editions seat a teamless spectator so an edition everyone in the test missed stays in the sequence, and `DisciplineWorld` for computed editions with discipline results; the `FAMILIES`/`KINDS` coverage of every `Discipline` subclass; `BADGES_QUERIES`; the progress counters and rows, and `World.tearDown`'s `assert_counters_agree()`, which replays each test's data edition by edition and checks every counter against its rule), `test_badge_refresh.py` (`refresh()`, a `master` lost then deleted, the progress diff, `refresh_due`, the command with and without `--if-due`, `BadgeAdmin`, the Edition action, the import hook) and the badge tests of `test_profiles.py` (the payload).

**Badge progress** (spec `2026-09-30-badge-progress-design.md`): how far a person is toward the 20 badges whose rule is a count, shown as a bar in the badge sheet (« 7 / 10 éditions »). `compute(today)` walks the same `History` as the rules, so a counter is the rule's own number and `BADGES_QUERIES` did not move: `_counters(h, reigns)` gives every person of `h.users` (the people, running editions included, zeros without a seat) their raw counters, and `_progress` turns them into `Progress` rows: a row per tiered code always (veteran, ever-present, networker, specialist, all-rounder), a row per other countable code only while it is not earned, with `value` null and `reachable` false once out of reach (eternal-second after a title, lucky-charm once one of the first three counted editions is off the podium, argonaut once the first edition is over without the person, argonaut having no row before), comrades while a partner is below 3 (0 without any teammate), nothing for the 42 others. Streaks store the current run in `value` and the best in `best`; on-the-rise counts rises (`max(rise − 1, 0)`); specialist names the discipline closest to its next tier, comrades the partner closest to 3 (`partner`), clean-sweep its best edition (`year`), each with tie-breaks in the spec, and a value of 0 names nothing. The target is not stored: it follows from the code and the value (the first threshold above it, above `best` for ever-present), from the tier tables and `PROGRESS_TARGETS` (the 14 other targets, which the rules read too), mirrored by the front's `TIER_THRESHOLDS` and `PROGRESS_TARGETS`. `BadgeProgress` (`models/BadgeProgress.py`, migration `0039_badgeprogress`, unique on `(user, code)`, not in the admin, not exported) holds them: `refresh()` diffs it by `(user, code)` in its transaction (`_store_progress`: delete, `bulk_update`, `bulk_create`, the rest untouched; 1 read plus 1 per kind of write, `REFRESH_OWN_QUERIES = 7` without writes). `refresh_due(today)` (1 query) returns `(due, refreshed_at)`: due without a refresh yet, when the last one's Paris date is at least `REFRESH_EVERY = 30` days before today, or when an active edition ended on or after that date and before today; `refresh_badges --if-due` refreshes only then. `GET /profile/<id>/` carries `progress` from `progress_entries(user_id)` (1 query, `partner__profile` joined): `[{code, value, best, reachable, discipline, partner, year}]` in catalogue order, `discipline` null when empty, the partner as in the badge entries (`_partner`); `/profiles/` rows carry none. A person added since the last refresh has no rows, and their sheets show what they showed before. Deploying it: `migrate`, run `refresh_badges` once (the table starts empty), and replace the host's monthly crontab line with the daily `--if-due` one.

**Player accounts** (spec `2026-09-24-player-profile-customization-design.md`, shipped in PRs #105 and #107): the registration import and `import_edition` create users with a random password nobody receives, so a player gets an account through a claim link an organiser generates and sends by hand, however they like (the app mails a claim link only through the one-off `send_claim_links` command, see below; the other mail it sends is the lost-password mail, over SMTP, see Lost password below), then logs in with the username and the password they chose there, through the usual `/auth/token/` and `/login`. `UserProfile` (`models/UserProfile.py`, migration `0035_userprofile`) holds what a person adds to their profile and how organisers moderate it: `user` (one-to-one, `related_name="profile"`), `photo` and `photo_small` (`ImageField`s under `avatars/`, see Player photos), `photo_locked`, `showcase` (an `ArrayField` of at most 5 codes whose choices are `Badge.Codes.choices`, see Badge showcase), `claimed_at` and `updated_at`. The row is created lazily (`get_or_create`) by a claim, a stored upload or a showcase save, never by `/me/`, a refused upload or a DELETE, and a missing row reads as no photo, the automatic showcase and unclaimed; it has no `is_active` (a one-to-one satellite of `User`, not edition data), so its admin skips `request_only_active`; it is not exported (`transfer.NOT_EXPORTED`); its `ImageField`s need Pillow (`requirements.txt`, so rebuild the server image). `claims.py`: a user is claimable when a person, `is_active`, and neither `is_staff` nor `is_superuser` (`unclaimable_reason` answers `STAFF`, `INACTIVE` or `NOT_A_PERSON` in that order, one query for the person check), so organisers keep their own passwords and no link hands over admin rights. `claim_link(user)` is `<PUBLIC_URL>/claim/<uidb64>/<token>` with a token from Django's `default_token_generator` (a hash of the password hash, `last_login`, the email and a timestamp: nothing stored, a link lasting `PASSWORD_RESET_TIMEOUT`, 7 days in `settings.py`, and every link of a person dying once any of them sets the password, a new one revoking none); it raises `ImproperlyConfigured` without an absolute http(s) `PUBLIC_URL` (`public_url()`), then `Unclaimable(reason)`. `check_claim(uidb64, token)` returns the claimable user of a valid, unexpired link or `None` whatever went wrong (only the canonical base64 of an id up to `2**31 - 1` reaches the database), and `complete_claim(user, token, password)` runs `validate_password` (the four `AUTH_PASSWORD_VALIDATORS`), then in one transaction re-reads the user under `select_for_update` and re-checks the token and claimability (`None`, changing nothing, when the link was used or the user made staff or deactivated meanwhile, so two uses of one link racing set one password), sets the password, deletes the user's DRF `Token` and creates a fresh one (every older session ends) and stamps `claimed_at`; it and the view carry `@sensitive_variables("password")`. The view `claimAccount` serves `GET`/`POST /claim/<uidb64>/<token>/` with `AllowAny` and `@authentication_classes([])` (the link is the credential: a stale token forwarded by the front must not 401 it). A link that does not hold is one identical 404 `{"error": "invalid_link"}` whatever the reason, so it tells nobody who exists; GET answers `{first_name, username}`; POST checks the link first, then answers 400 `{"errors": ["password_missing"]}` for a body that cannot be parsed or an absent, blank or non-string `password`, 400 `{"errors": [<Django codes>]}` for a validator refusal (`password_too_short`, `password_too_common`, `password_entirely_numeric`, `password_too_similar`), and `{token, user_id}` on success. Organisers make links with the admin action « Générer un lien d'activation » on `PlayerAdmin` and `UserProfileAdmin` (`ClaimLinksPermission`: `has_claim_permission` asks `auth.change_user`, whatever the organiser's rights on players or profiles, since a link sets a password): one message line per user of the selection in name order (several players of one person make one line), `Léa Martin (leamartin) : <link>`, a warning naming why for a staff, deactivated or non-person user (`CLAIM_REFUSALS`), or, without a usable `PUBLIC_URL`, one error line and no link; the links travel only in Django's messages, never logged. `GET /me/` (`getMe`, `IsAuthenticated`) answers anyone logged in, an organiser who never played included: `{id, first_name, last_name, username, email, is_staff, is_person, photo: {large, small} | null, photo_locked, showcase: {auto, codes}}` (`email` blank when none, the owner's alone) (`MeSerializer`, `codes` the stored pins as left, `auto` when there is none). Since the front calls it on every page carrying a token, it computes no badge, standing or leaderboard: the token, then one query reading the profile row (`select_related`) and the person flag (an `Exists` over `person_players()`), `ME_QUERIES = 2` in `test_me.py`, and it never creates the row. **Account management** (spec `2026-10-02-account-management-design.md`): `accounts.py` holds what a logged-in person does to their own account, the views checking who the caller is and throttling: `password_ok(user, password)` (a non-string never is), `change_email` (stripped, lower-cased, `ValidationError` code `invalid_email`, no verification), `change_password` (`validate_password`, then the password and a replaced DRF token in one transaction, returning the key; the front stores it) and `deactivate(user)`: in one transaction under `select_for_update`, `avatars.remove_photo` (files go on commit), `showcase` cleared, `UserProfile.anonymized` set (row created if missing), `is_active` off, an unusable password (a reactivation never revives the old one, nor any older claim or reset link, since the token hashes the password) and the DRF token deleted; the `Player` rows stay, so places, badges and the leaderboard position remain. `UserProfile.anonymized` (migration `0040_userprofile_anonymized`) makes every public payload serve (`TestNoPublicRouteLeaksAnAnonymizedPerson` in `test_anonymity.py` walks every `PUBLIC` route of `test_permissions.py` for an anonymized person's real names, username and email) `("Joueur", "anonyme")` through `anonymity.shown_names(user)`, which reads the loaded `profile` relation (no row reads as not anonymized): `SummaryPlayerSerializer`'s name getters, `profiles.py` (the leaderboard and the profile record, the discipline all-time rows through the same record) and the `comrades` partner in `badges.py`; callers serving many users join `user__profile`, so the query-count constants did not move. The real name stays in the database, so it is display-level only, and the roster order still follows the real surname. `store_photo` refuses an anonymized profile like a locked one (`photo_locked`); `UserProfileAdmin` shows and filters `anonymized` and edits it. An organiser reactivates a person by unticking `anonymized` on the profile, ticking `is_active` on the user in the user admin, and generating a claim link (the old password is gone). `complete_claim` stamps `claimed_at` once: a reset later keeps the first activation date. **Lost password**: `password_reset.py` (the mail's « valable N jours » follows `PASSWORD_RESET_TIMEOUT`, rounded up to whole days), `send_reset(email)` finds the user by `email__iexact` among active users and mails only when exactly one active user has it (`user_for_email`: a deactivated account, which keeps its email, is not looked up; several active users sharing an address match nobody, so one address cannot reset another person's account) and that user may reset (`claims.unresettable_reason`: active, and either an organiser, staff or superuser, who never plays and gets no `UserProfile` row from a reset, or a person; unlike a claim link, which an organiser hands to someone else and so never serves staff, a reset link goes only to the account's own address; `claim_link(user, route="reset")`, the `/reset/<uid>/<token>` page, valid and invalidated like a claim link, `check_claim`/`complete_claim` taking the eligibility rule itself (`rule=unresettable_reason` from `resetPassword`, the claim rule `unclaimable_reason` by default; `claims.LINK_RULES` maps a link's route to its rule) while the claim endpoint still refuses a staff user, a reset token included); a missing `PUBLIC_URL` or a false `settings.MAIL_CAN_SEND` (SMTP without an `EMAIL_HOST`) logs an error and sends nothing. The mail leaves on a daemon thread (`dispatch`, failures logged, never raised), so the request takes the same time whether or not an address matched. Deactivated and non-person users, unknown and shared addresses are silent to the caller, but each logs its reason at INFO on `olympic_warriors.password_reset` (by user id, never by address), as do « queued » and « accepted by the mail server »: « accepted » only means the SMTP server took the mail, so a provider that then blocks it (Mailjet does for a sender address or domain not yet validated in its dashboard, with no error on our side) is told apart from a mail never sent. The `olympic_warriors` logger writes to the console in `LOGGING`, so `docker compose logs server` shows these lines (only WARNING and above did before). Mail settings: see Settings. `test_accounts.py`, `test_me_account.py` (the three `/me/` writes), `test_password_reset.py` and the anonymized cases of `test_showcase.py` cover it. `test_claims.py` covers claimability, `PUBLIC_URL`, the link's lifecycle and its 404s, the validators, the race (a `TransactionTestCase`), the throttle and the admin action with its permission.

**Mailing claim links** (spec `2026-10-04-send-claim-links-design.md`): `manage.py send_claim_links [--dry-run]` (logic in `claim_mailing.py`) mails each person without an account their claim link, once, from the host. Recipients are active, non-staff people (an active player in an active edition) with no `claimed_at` and a valid email that is not `@olympicwarriors.com` (subdomains included); the others are skipped and counted by reason. Users sharing an address are each mailed and the command warns about the address (self-reset matches nobody for it). It needs `PUBLIC_URL` and `MAIL_CAN_SEND`, a failed mail is logged by user id and counted without stopping the batch, and re-running mails a fresh link to whoever has not claimed yet (nothing is stored). `test_claim_mailing.py` covers it.

**Player photos:** `olympic_warriors/avatars.py` writes and deletes the files, outside `save()` since it touches the filesystem, not business rules. `store_photo(profile, upload)` raises `PhotoError` (its `code` is the API's) for a locked profile (`photo_locked`, checked again on the row re-read under `select_for_update`), no file (`missing`), more than 2 MiB (`MAX_BYTES`, `too_large`), anything but a JPEG, PNG or WebP (`bad_format`: only those parsers ever read an upload, and a multi-picture JPEG, which opens as MPO, passes with its first picture), and more than 4096² pixels in total (`MAX_PIXELS`), read from the header between `open()` and `load()` so nothing is decoded, Pillow's own decompression-bomb guard counting too (`too_many_pixels`). It then decodes a JPEG through `draft` at the smallest scale keeping 1024px (`DRAFT`), turns the picture upright from its EXIF orientation through its own `UPRIGHT` table (an unreadable block or orientation means no turn, never a refusal), crops the centred square, flattens any transparency onto mid grey (`BACKGROUND`, 128/128/128, the grey the browser's export fills with), converts to RGB with no metadata left (no EXIF, GPS included, no ICC or XMP), and writes a 512px and a 128px WebP at quality 82 (LANCZOS) under fresh random names (`avatars/<user id>-<12 hex>.webp` and `…-sm.webp`: a URL never changes content, so it can be cached forever). The files the row pointed at go once the transaction commits (`delete_on_commit`, one robust `on_commit` callback per file), the ones it wrote at once if its own block fails. `remove_photo(profile)` clears both fields the same way, locked or not, and returns whether there was a photo (without one it writes nothing). A deleted profile, its user's cascade included, takes its files with it: a `post_delete` receiver in `signals.py`. `photo_urls(profile)` (`{large, small}`, site-relative `/media/avatars/…`, or `None` without a row or a photo) and `small_photo_url` cost no query. `PUT /me/photo/` (`myPhoto`, `IsAuthenticated`, a multipart `photo`) answers, in order, 404 `{"error": "not_a_person"}` for a user who is not a person, 403 `{"error": "photo_locked"}`, 400 `{"error": "too_large"}` from `Content-Length` alone above `MAX_BYTES` + `MULTIPART_ALLOWANCE` (64 KiB) before a byte of the body is read, then `store_photo`'s 400 codes (a 403 when locked meanwhile), else 200 `{photo: {large, small}}`; the row it creates for a first upload rolls back with a refusal. `DELETE /me/photo/` answers 204 with or without a photo, locked or not, creates no row and is never throttled: a person can always take their face down (404 for a non-person too). `UserProfileAdmin` moderates: the columns name, thumbnail, `photo_locked` (`list_editable`), `claimed_at` and `updated_at`; search by names and username; the filters `photo_locked`, has photo and claimed; no add; the actions « Retirer la photo », « Retirer et verrouiller » (the lock then the removal in one transaction per profile, so an upload waiting on the row finds the lock) and « Générer un lien d'activation », the stock bulk delete dropped (a profile can still be deleted from its own page, its files going with it). The change form edits only the lock: the photo shows as a thumbnail linking to the full size with no upload widget (every face on the site was put there by its owner), the pins by name, and the empty value for no photo or no pins. Tests: `test_avatars.py` (`MediaRootTestCase`, a throwaway `MEDIA_ROOT` per test, which `test_me.py` and `test_user_profile_admin.py` reuse), `test_me.py` (`/me/` and `ME_QUERIES`, the uploads and their refusals, the body refused unread, the delete, the throttle) and `test_user_profile_admin.py`.

**Badge showcase:** five badges on a person's profile header and leaderboard row (three until 2026-09-30, migration `0038_userprofile_showcase_five`: Postgres ignores an array's declared size, so it changes no stored row). `UserProfile.showcase` repeats `SHOWCASE_SIZE` as its `size`, since `badges.py` imports the models, and `test_showcase.py` keeps the two in step, as `badge-codes.test.js` does the front's. The stored pins are `UserProfile.showcase`, `PlayerRecord.pins` and `/me/`'s `showcase.codes`, while "showcase" in the public payloads is the computed `{auto, badges}` (a row's is its `badges` alone). `badges.showcase(entries, pins, holders)` computes it with no query, from `profile_badges` entries, the pins and `badge_stats(...)["holders"]` over the leaderboard's people: the pins still earned, in the person's order (a pin revoked or recomputed away stops showing, and none left means automatic), else (`auto`) the `SHOWCASE_SIZE = 5` rarest earned codes, fewest holders first (a code without a count has none), then the higher tier held, then catalogue order; each drawn from the entry with the highest tier, the first among equals, as the front's collection slot picks its medallion (`{code, tier, discipline}`, never a partner). `/profile/<id>/` passes it the person's `profile_badges`, `record.pins` and its `badge_stats`, and `/profiles/` does the same for every row from `badges_by_user` and one `badge_stats` over everyone listed, so a row shows exactly its profile's badges. `PUT /me/showcase/` (`setMyShowcase`, `IsAuthenticated`, JSON `{codes}`) stores 0 to 5 distinct catalogue codes, each earned now (`badges.valid_pins`; `[]` is back to automatic), answers 400 `{"error": "invalid_showcase"}` for anything else, an unreadable body included (404 for a non-person), writes the `showcase` field alone (a photo stored meanwhile survives) and answers the new `{auto, badges}`, its rarity over `person_ids()`, in `SHOWCASE_PUT_QUERIES = 7` (3 more on the save that creates the row, `test_me.py`). A catalogue change migrates the field's choices too, as `0037_alter_userprofile_showcase` did for `master` (after `0036`, the merge of the two `0035`s); a migration that removes a code (as `0034` did for the Badge rows) should also drop it from the stored pins, which otherwise linger, harmless: the showcase shows earned codes only, and the admin prints an unknown code as is. `test_showcase.py` covers `showcase()`, `badges_by_user`, `person_ids` against the leaderboard and the payloads.

**Soft deletes:** nearly every model has `is_active`; the admin injects `is_active__exact=1` into every changelist via `request_only_active`, so inactive rows are hidden but still exist.

Settings: `olympic_warriors/config.py` (pydantic-settings) reads `ENV` and loads `DevConfig`/`ProdConfig`; any other value silently yields an empty config. `DATABASE_URL` wins over the `DB_*` vars. `PUBLIC_URL`, the front's public address and the base of the claim links, is optional (`http://localhost:5173` in `DevConfig`, empty otherwise), so a deploy never fails on it: without an absolute http(s) value the admin action refuses to make links and the rest works; `LOGIN_THROTTLE_RATE`, `PHOTO_THROTTLE_RATE`, `PASSWORD_THROTTLE_RATE`, `RESET_EMAIL_THROTTLE_RATE` and `NUM_PROXIES` are described under API. Outgoing mail (password reset) is optional like `PUBLIC_URL`: `EMAIL_HOST` (empty), `EMAIL_PORT` (587), `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_TLS` (true) and `DEFAULT_FROM_EMAIL` (`Olympic Warriors <noreply@localhost>`) feed Django's `EMAIL_*`; with no `EMAIL_HOST`, `ENV=dev` uses the console backend (the mail prints in the server log) and any other env keeps SMTP so a reset request logs an error instead of vanishing; `settings.py` derives the backend and `MAIL_CAN_SEND` from one condition, which `send_reset` reads. Media is served by Django only when `ENV=dev`, where the Vite dev server proxies `/media` to `API_URL` (`vite.config.js`, `changeOrigin`), since the payloads carry site-relative photo URLs. `settings.py` creates the `LOG_FILE` folder (`server/logs/`, gitignored) at import, so a fresh clone needs no `mkdir`. `Dockerfile.prod`/`Dockerfile.stage` run `collectstatic` with `ENV=prod`, so their build context needs `prod.env` (at least `SECRET_KEY`, `DEBUG`, `DB_*`) and no `dev.env`. Deploying the player accounts: `migrate` (`0035_userprofile` to `0037`) and rebuild the server image (Pillow); set `PUBLIC_URL` in the `prod.env` of prod and of stage, each its own public address, or the admin makes no claim link; deploy the server before the front, since a new front on an old server gets a 404 from `/me/` and counts every token, an organiser's included, as a visitor; the photo URLs are site-relative, so the nginx server block of the **front's** public host must serve `/media/avatars/`, for example `location /media/avatars/ { alias /home/app/web/mediafiles/avatars/; expires max; }` (where `docker-compose.prod.example.yml` mounts the media volume in the nginx container; stage's is under `/home/stage/web/`), serving public folders only and never `registration_forms/`, which holds the registration CSVs with names and emails; and add the `mediafiles` volume to the host's backups, since players' photos cannot be re-created from the admin. Deploying account management: `migrate` (to `0040_userprofile_anonymized`), set the SMTP variables (and optionally the two throttle rates) in the `prod.env` of prod and of stage, each with its own `PUBLIC_URL`, rebuild both images and deploy the server before the front (an old server answers the new front's account calls with 404). Deploying the badge progress: `migrate` (`0039_badgeprogress`), run `refresh_badges` once, and replace the host's monthly crontab line with the daily `--if-due` one (see Badge progress).

Known limitations of account management: an email shared by two active users switches off self-reset for both (nobody matches; a deactivated account is not looked up, so it never blocks the live one), and since email changes are unverified a player can type another's address or a typo, which silently breaks their own reset (an organiser's claim link is the fallback); anonymization is display-level (the real name stays in the database and a roster's order still follows the real surname); and a deletion shows no notice, the visitor just lands on `/`.

Known dead code: `olympic_warriors/models.py` (shadowed by the `models/` package) and the unused `bootstrap5`/`crispy_forms` apps. `olympic_warriors/templates/` holds only the Badge changelist override.

## Frontend architecture

**Every edition page is under a year segment.** `front/src/params/year.js` matches exactly four digits, so `[year=year]` never swallows `/login`: the routes are `/<year>` (hub), `/<year>/ranking` (the one list of teams: podium, rosters, points, with the discipline rail under the title), `/<year>/disciplines`, `/<year>/disciplines/<id>`, `/<year>/teams/<id>`; `/<year>/teams` is a `+page.server.js`-only 302 to that year's ranking, kept for old links since the teams grid merged into the ranking. `/` renders the latest edition's hub through the same `front/src/lib/components/EditionHub.svelte` as `/<year>`, without redirecting. The bare `/ranking`, `/teams` and `/disciplines` are `+page.server.js`-only 302 redirects to the latest year (`/teams` straight to its ranking). Detail routes take a numeric id, not a slug. **Two languages, French first.** Every visible string goes through `t` from `front/src/lib/i18n/`: `fr.js` is the reference dictionary, `en.js` mirrors it key for key (`parity.test.js` fails otherwise), counting messages are `{ one, other }` picked with `Intl.PluralRules` (French puts 0 in the singular: `0 match`), and `disciplines.js` maps database discipline names to French (`icons.test.js` fails when a model is in neither `FRENCH_NAMES` nor `SAME_IN_FRENCH`). The locale comes from the `lang` cookie: the root `+layout.server.js` reads it through `localeFrom` (anything but `en` is `fr`), `+layout.svelte` puts it in Svelte context under `I18N`, and components call `useT()` / `useLocale()` at init only (Svelte's `getContext` throws anywhere else). `hooks.server.js` sets `<html lang>` from the same cookie and `Vary: Cookie`, and serialises `content-type` for universal loads' SSR fetches. The theme follows the same pattern with no layout data: `hooks.server.js` writes `<html data-theme>` from the `theme` cookie (`light`, `dark`, or `system` without one, `$lib/theme.js`), and the header's sun/moon form posts to `/theme`, whose action stores `light` or `dark` for a year (`system` or anything else deletes the cookie, handing the theme back to the device) and 303-redirects like `/lang`. Only the browser knows which theme is on screen and which one the device prefers, so the header renders four buttons (`SWITCHES`: each direction storing a choice, and each posting `system`) and its stylesheet shows one: the direction away from the theme on screen, posting `system` when that direction is the device's own theme, so toggling twice returns to the device and the cookie only records a departure from it. A browser without `:has()` gets no switch (`@supports not selector(:has(a))`), since it never leaves dark. `/lang`, `/theme` and `/logout` share the redirect guard `localPath` from `$lib/local-path.js`. The header's `FR | EN` form posts to `/lang`, whose action stores the cookie for a year and 303-redirects to the local path it was given, so the page reloads fully in the new language and no client code decides it (never `use:enhance` that form). Helpers in `edition.js` carry no language: `formatDateRange` and `ordinal` take the locale as last argument (`1er octobre`, `1re`, `2e` in French; anything but `en` is French), `disciplineSubtitle`/`roundCount` return counts the pages word, and an unknown team name is `null` (`GameRow` and the discipline page print `team.unknown`). `+error.svelte` words a 404 as `error.notFound` and every other error as `error.generic` outside dev, since thrown messages are English by construction; `error.html` is served before any layout and carries both languages. To move to Paraglide or svelte-i18n later: the flat key files convert directly, every call site is a `t(key, params)` and the locale is resolved in one place.
